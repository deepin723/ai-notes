## 这个项目在解决什么问题

Claude Code 本身很强，但它是单线程工作的——你交给它一个任务，它一步步做，等它做完再做下一个。

当任务复杂到需要"同时让多个 Agent 并行工作"时，就需要一个编排层。

ruflo 就是这个层。它在 Claude Code 之上，加了：
- 100+ 个预设专业 Agent（代码、测试、安全、文档、架构……）
- Agent 之间的通信协议
- 跨机器、跨组织的 Agent 联邦
- 自学习记忆系统（每次任务都在改进下次的策略）

一句话：**ruflo 是 Claude 的多 Agent 操作系统**。

---

## 架构设计：几个有意思的地方

### WASM 内核 + Rust 策略引擎

底层用 Rust 写了策略引擎、向量嵌入和证明系统，编译成 WASM 运行。

为什么？两个理由：
1. Rust 的内存安全 + 性能，适合做需要低延迟的 Agent 路由决策
2. WASM 可以在任何环境运行，不依赖特定 OS，方便跨平台部署

这说明项目不只是个"包装一下 API 的工具"，底层有真实的性能考量。

### 两种安装路径，设计思路清晰

| 路径 | 内容 | 适用 |
|------|------|------|
| Claude Code Plugin（轻量）| 只加 slash commands，没有 MCP server | 试用，不想改变现有工作流 |
| CLI 全量安装 | 98 个 Agent + 60+ 命令 + MCP server + hooks + daemon | 生产使用 |

这个设计很成熟：**渐进式引入，降低初始心理门槛**。先装个轻量版试试，觉得好再升级。很多开源项目忘了"让人上车"这件事，直接甩一个复杂的全量安装，劝退大部分潜在用户。

### 自学习循环（Self-Learning Loop）

```
User → Router → Swarm → Agents → Memory → LLM
                                    ↑           |
                                    ← Learning ←
```

每次任务执行完，成功的 pattern 会被存入 ReasoningBank，下次遇到类似任务，直接复用已知的有效策略，不从零开始。

这个设计的核心价值是：**系统会随使用而变好**，而不是永远在同一水平。

## 它和其他 Agent 框架的区别在哪

目前比较流行的 Agent 框架：LangGraph、AutoGen、CrewAI。

ruflo 的差异化点：
- **深度绑定 Claude Code**：不是通用框架，是专门为 Claude 的工作方式设计的
- **企业级安全**：内置零信任联邦通信，Agent 之间的数据交换有加密和权限控制
- **WASM 内核**：性能和可移植性不是事后补丁，是架构设计

但也有代价：**深绑 Claude = 强依赖 Anthropic 的生态**。如果将来 Claude API 定价大幅变化，或者 Claude Code 的接口改了，ruflo 受影响会比通用框架更大。

## 我对这类工具的整体判断

Multi-agent 编排框架这条路是真实需求，但目前生态还很碎——每个框架都在定义自己的 API、自己的 Agent 协议，互不兼容。

这让我想到 2010 年代初的 JavaScript 框架大战（Backbone、Ember、Angular、React……），最终赢的不一定是最早的，而是设计得最简洁、最好上手的。

ruflo 目前的方向是"全家桶"——功能多但学习曲线陡。在 AI Agent 这个赛道上，谁先做到"5 分钟上手，真实解决一个问题"，才最有可能成为这个时代的 React。

## 实际使用价值评估

**适合**：
- 在做 AI 自动化流水线、需要多步骤并行工作的场景
- 深度 Claude Code 用户，愿意花时间学习配置
- 企业内部需要多 Agent 协作的团队

**不适合**：
- 只是偶尔用 Claude Code 写写代码
- 不想修改现有工作流
- 对 Rust + WASM 技术栈不熟悉，遇到问题难以调试

这不是一个"装上就能用"的工具，是一个"投入精力才能发挥价值"的工具。

## 一个题外话

项目名字由来很有趣：作者叫 rUv，喜欢 Rust、喜欢心流（flow state）。"Ru" 是人，"flo" 是流。命名是产品价值观的外化——一个工具的名字，就说清楚了它想成为什么。
