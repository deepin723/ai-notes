角色 demo 好玩之后，怎样接到同一个肉鸽关卡？当前项目没有把四套 demo 简单拼成一个超大文件，而是增加共同的关卡与成长层，同时保留各角色自己的动画和战斗控制。

## 一、正式试玩的结构

```text
角色选择页面
  ├─ 小焰适配入口 ─ 小焰动作与渲染
  ├─ 紫魇适配入口 ─ 狼人动作与渲染
  ├─ 幽灯适配入口 ─ 幽灯 core + growth
  └─ 机兵适配入口 ─ 机兵 core + growth
           │
           └─ GrowthRun：经验、升级、选牌、敌人节奏、结算
                        └─ CombatRuntime：伤害事件与统计
```

`reports/two-hero-growth-20260914/play/run.mjs` 是共同流程。目录名字虽叫 two-hero，目前角色选择已经有四人。旧 README 开头是历史双角色描述，文件后面的“四角色接入”追加说明才对应当前扩展；本系列以实际代码为准。

## 二、适配器如何像前端接口一样工作

四角色内部状态不同，有的叫 `maxhp`，有的叫 `maxHp`；角色高度与技能也不同。成长层通过 adapter 获取玩家、敌人、暂停和刷怪等能力，避免直接写死某个角色的内部实现。

教学接口示意，不是 TypeScript 已生成定义：

```ts
interface HeroAdapter {
  height: number;
  player(): Player;
  enemies(): Enemy[];
  pause(value: boolean): void;
  spawn(x: number, y: number, elite: boolean, runner: boolean): Enemy;
  apply?(cardId: string): void;
  unlock?(): void;
}
```

`Player/Enemy` 是这里省略的游戏状态类型。这个结构很像业务系统给不同后端写 adapter：公共层只认稳定接口，内部细节由角色模块处理。

## 三、选卡暂停是一种正式游戏状态

`GrowthRun` 当前包含 ready、playing、paused、draft、won、dead 等状态。

```text
ready → playing → draft → playing
             ↘ paused ↗
             ↘ dead
             ↘ won
```

进入 draft 后，成长层暂停角色适配器；游戏 step 在非 playing 时不推进。这比“只显示一层遮罩”可靠，因为遮罩后面的子弹、冷却和敌人都不应继续偷偷运行。

选择卡牌后写入等级、调用对应 apply 行为、恢复 playing，并给予短暂无敌。若已有经验足以再升一级，会再次进入选卡，不能因为一次只弹一张卡就丢掉多余经验。

## 四、卡牌其实是数据加行为

`cards.mjs` 的一张真实卡是机兵 K1“高速弹仓”：默认每五轮普攻触发，选一次改为四轮，再选一次改为三轮。它保存 hero、route、max、min 和分级描述。

```js
// 根据真实卡牌与成长钩子展开。
const card = {
  id: 'K1', name: '高速弹仓', hero: 'cleaver', route: 'pulse',
  max: 2, min: 2,
  desc: ['每五轮改为每四轮触发。', '每三轮触发。']
};
function applyCards(game, run) {
  game.passiveEvery = 5 - run.count('K1');
}
```

卡牌描述不会自动产生效果。前端最容易做出“文案变化了但游戏没变”：选择后只更新卡片 UI，没有把参数送到发射逻辑。反过来，参数生效了但 HUD 仍显示旧冷却，也会让玩家困惑。

参数最好从基础值和卡牌等级计算，避免每次刷新 apply 时都 `damage *= 1.2`，导致重复叠乘。延长现存魂灯寿命等状态迁移则单独处理，不能只改下一盏灯。

## 五、三选一为何不直接随机抽三张

当前卡池有 48 张：小焰 18、紫魇 8、幽灯 8、机兵 8、通用 6。这里的张数是不同 card ID 数量，不是累计升级等级数。

首先过滤其他角色、等级不够和已满级卡。首次升级给每个角色固定三个起手方向。之后大致优先当前主修，再给角色内部组合方向，最后提供通用生存项；不够三张时再从合格池补齐，避免重复。

这是引导构筑的一个简单方案，不是成熟的概率平衡系统。当前 `focus` 随最近选择的角色卡路线变化，不代表完整计算了“玩家真正最强流派”。将来可用卡牌投入和已有组合权重进一步改进。

选卡同时应在逻辑层验证：玩家提交的 ID 必须属于本轮 choices，而不只是 UI 上隐藏非法按钮。`choose()` 已检查当前状态和选择范围。

## 六、关卡导演也只是持续运行的逻辑

这版第一夜是 180 秒流程，等级从 1 到 8，最多七次升级选择。130 秒生成厚皮精英，满 180 秒且精英已击倒才胜利；因此精英没死时，并不是时间一到强行结算。

当前经验门槛数组为 `5, 7, 9, 12, 15, 19, 23`。经验从死亡敌人掉落，靠近拾取才加到玩家身上。`GrowthRun` 控制刷怪数量上限、普通/奔跑敌人和短喘息段，低血量时也会放慢刷怪。

这些数值只是当前可玩版本参数，不是“最优肉鸽公式”。文档应解释参数控制什么体验：门槛决定成长节奏，上限决定拥挤程度，刷怪间隔决定压力上升速度，精英时间决定后段目标。

## 七、延迟效果为什么使用游戏时间

`GrowthRun.after()` 将任务保存为 `at: run.time + seconds`。step 只执行到期任务。与直接 `setTimeout()` 相比，这让暂停时延迟伤害也暂停。

```js
function after(seconds, fn) {
  jobs.push({ at: gameTime + seconds, fn });
}
```

这只是示意。完整实现还应处理重开清理、结束状态、目标已死，以及卡牌参数按施放时还是命中时计算。当前 README 也明确指出，并非所有飞行中攻击都已统一为施放时参数快照；不要把尚待改进的地方写成已经完成。

## 八、生成适配器的便利与风险

`build-adapters.py` 处理小焰/紫魇，`build-new-adapters.py` 处理幽灯/机兵。它们从已认可的独立 demo 生成关卡适配文件，靠指定文本锚点替换部分逻辑，方便保留视觉效果。

代价是文本替换比较脆：上游改了代码格式，锚点可能找不到。因此生成器会检查锚点；要修改生成逻辑，应先改生成器再生成，而不是只改 `ember.mjs` 然后下次被覆盖。

长期更合适的方向是把稳定的角色 core 和 renderer 抽成正式模块，通过配置与接口注入成长行为。这里是在解释当前阶段的实现取舍，不宣称现在已经重构成完美引擎。

## 九、测试一张卡要观察行为

以 K1 为例：不只断言卡片文字变成“每四轮”，而是实际发射四轮，检查共振次数。以幽灯 H2 为例：三次完整普攻之后生成灯，命中多个目标不多计数；无目标时保留充能。以升级为例：弹出选卡后推进几秒，战场时间不能增加。

当前测试入口可查看 `play/run.test.mjs`、`new-heroes.test.mjs`、`ember-growth.test.mjs`、`wraith-growth.test.mjs`。自动战斗通过只能说明流程跑通，不能代替对难度、手感和视觉的人工试玩。

## 十、自己的练习

只做两张卡：“每五发强化改每四发”和“强化弹多一枚追踪弹”。让第一张改触发频率，第二张改输出结构，再观察它们组合时的实际行为。这个练习比一次写二十张纯伤害百分比卡，更能帮助理解成长系统。
