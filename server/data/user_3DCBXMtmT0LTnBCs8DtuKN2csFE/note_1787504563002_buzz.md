项目地址：[block/buzz](https://github.com/block/buzz) · Rust · 30.0k stars · 今日约 410 stars

## 不是再做一个聊天机器人

Block 开源的 Buzz 想做一个人类与 Agent 共用的协作空间。它最关键的设计是：消息、反应、审批、工作流步骤和 Git 事件都被表示成同一种带签名事件，写入 Nostr Relay。人和 Agent 使用同一套身份、频道和审计模型，Agent 不再是躲在 webhook 后面的“幽灵定时任务”，而是拥有独立密钥、成员关系和行为记录的协作者。

在产品层，它像团队聊天、代码托管、自动化和项目记忆的混合体；在技术层，它是一条统一事件日志。频道可以绑定功能分支，补丁、CI、评审与合并决定留在同一个上下文中。Agent 可以通过面向机器的 `buzz-cli` 使用 JSON 输入输出，也能通过 ACP 连接 Codex、Claude Code、Goose 等工具。

## 架构骨架

Buzz 是一个较大的 Rust workspace：Relay 使用 Axum WebSocket 与 REST；Postgres 保存事件并提供全文搜索；Redis 负责 pub/sub；S3/MinIO 保存媒体；认证使用 NIP-42/98；Git 补丁采用 NIP-34 事件；审计记录带哈希链。桌面端则是 Tauri + React。

项目很坦率地区分了“已经可用”和“正在接线”：频道、线程、私信、搜索、审计、桌面端、Agent CLI 与 YAML 工作流已经存在；移动端、审批闸门和部分 huddle 生命周期仍在完善。这个区分比宏大的愿景本身更值得信任。

## 我的判断

Buzz 抓住了 Agent 协作的真正瓶颈：不是模型不会写代码，而是缺少共享状态、身份边界、证据链和可追溯决策。把人、Agent、工作流和 Git 统一成事件，是一种比“在 Slack 里加个机器人”更彻底的设计。

代价是范围极大。聊天、代码托管、媒体、语音、工作流和审计任何一项都足以成为独立产品；Nostr 事件模型是否适合复杂企业权限、撤销、合规保留和数据隔离，也需要真实团队验证。现在更适合把它看成一个有完整代码的强观点实验，而不是成熟的 Slack/GitHub 替代品。

## 对我的启示

多 Agent 系统要先设计“共同记忆和责任归属”，再设计提示词。每个动作若都能回答是谁做的、基于什么证据、经过谁批准、后来如何修改，Agent 才可能真正进入团队生产流程。
