## 核心观点

作者一句话点破 Agent 做 demo 和做真实工程的核心差距：

> **Demo 里的工具通常都成功。真实世界里的工具不一定。**
>
> 一个可靠的 Agent，成熟度不取决于它能跑多远，而取决于它出错时有没有刹车、有没有解释、有没有边界。

这句话我同意 100%。

---

## 具体问题：失败了，Agent 该怎么办

作者举的例子很具象：

```
任务：帮我查订单 A1001 的物流，如果没送达，再查延迟补偿政策。

理想流程：查订单 → 判断 → 查政策 → 给建议

真实可能发生：
- 订单接口超时
- 订单不存在
- 用户没权限查这个订单
- 政策搜索没结果
- 工具参数缺失
- 高风险操作需要用户确认
```

没有失败策略的 Agent 会做出糟糕行为：
- 接口超时直接放弃
- 订单不存在还继续查政策（没意义）
- 权限不足却假装查到了（危险）
- 政策为空却编一个政策（**这是 agent 最大的安全漏洞**）
- 连续重试同一步，卡到超时

## 作者给出的框架：错误分类 → 映射策略

### 第一步：把错误类型结构化

```typescript
type ToolErrorType =
  | "invalid_arguments"
  | "unknown_tool"
  | "not_found"
  | "timeout"
  | "permission_denied"
  | "confirmation_required"
  | "empty_result";
```

**不是一个笼统的 `{ok: false, error: "执行失败"}`**，而是让每种错误有明确语义。

### 第二步：错误 → 策略的映射表

```typescript
const failureStrategies = {
  timeout:              "retry",    // 网络抖动，重试
  empty_result:         "fallback", // 查不到，降级回答
  not_found:            "stop",     // 资源不存在，停止
  invalid_arguments:    "stop",     // 参数错，别硬撑
  unknown_tool:         "stop",     // 工具不存在，停止
  permission_denied:    "stop",     // 权限不够，停止
  confirmation_required:"pause"     // 风险操作，等确认
};
```

这张表朴素到可笑，但它把"失败了怎么办"从**一句模糊的话**变成了**明确的工程策略**。

## 文章里我最认可的三条原则

### ① 重试要克制，不要把 retry 当万能药

```typescript
function canRetry(step, result) {
  return !result.ok
      && result.errorType === "timeout"
      && step.retryCount < step.maxRetries;
}
```

关键是这个 **必须同时满足三个条件**：是失败、是超时、没超过次数上限。

作者原话："**没有上限的重试，不叫韧性，叫迷路。**"

真实工程里，我见过太多"无脑 retry 3 次"的代码最后变成"无脑 retry 3 次 × 每个 step × 每个并发任务 = 几百次调用浪费"。

### ② 降级 ≠ 糊弄用户

降级是：
- 告诉用户哪些信息查到了
- 告诉用户哪些没查到
- **不编造不存在的依据**
- 给下一步建议

错误做法：为了"答案完整"让模型编一个政策填进去。
正确做法：

> 我查到了订单 A1001 当前仍在运输中，但**没有找到明确的延迟补偿政策**。建议联系人工客服确认是否可申请补偿。

这比假装搞定了、用户用出问题更可靠。

### ③ 暂停也是一种能力

对高风险操作（取消订单、删除文件、发钱），Agent 的正确行为不是判断后立刻执行，也不是"遇到错误就放弃"，而是：

```
这个操作会取消订单 A1001。请确认是否继续。
```

**"知道什么时候停下来问用户"比"能自主完成任务"更难做、也更重要**。

## 我的判断：这篇文章触及了 Agent 工程化的真正门槛

过去半年我看过大量"我 30 分钟搭了个 AI Agent"的教程。99% 都在教：
- 怎么定义 tool schema
- 怎么写 system prompt
- 怎么 loop（Plan-Act-Observe）

**几乎没人讲错误处理**。

这不是因为错误处理不重要，而是因为：
1. 做 demo 不会遇到（环境干净）
2. 做到真实场景才会踩坑
3. 踩了坑后写文章的人很少（已经忙着救火了）

这也是为什么绝大多数 Agent 产品 Demo 很惊艳、上生产就翻车——**工具调用成功时它很智能，工具失败时它表现得比 if/else 还糟糕**。

## 这套框架能迁移到非 AI 项目吗

能。其实作者这套 **ToolErrorType → FailureStrategy** 的思路，就是 **Erlang/OTP** 的 *let it crash* 加上 *supervisor* 策略的现代版。

Erlang 20 年前就懂：
- 不同错误要不同处理
- 有的错误重启，有的错误升级
- 有的错误立刻停，有的错误等人工介入

**Agent 工程化其实是在重新学 Erlang 教过的课**。

## 对我的启示

1. **下次写 Agent 工具时，第一件事是列出这个工具所有可能的失败模式**，而不是先写 success path。

2. **错误返回结构化类型，不要只返回字符串**。`{errorType: "timeout"}` 对下游 agent 的决策能力远大于 `{error: "超时了"}`。

3. **把"暂停"当成一个一等公民状态**。Agent 框架里应该有 `pending_confirmation` 这个状态，像数据库的事务一样——用户没确认，就永远等着，不降级也不放弃。

4. **建立"重试黑名单"**：哪些错误重试一定没用（参数错、权限错、资源不存在）——这些直接 stop，别浪费 token 和时间。

5. **压测 Agent 时一定要故意注入失败**：强制接口超时、强制权限拒绝、强制空结果。这些场景跑不通，你的 Agent 上生产就是灾难。

## 一个延伸问题

如果要给 Agent 框架加一个新能力，它应该是什么？

我的答案：**自我观测和解释能力**——Agent 遇到失败时，不只是处理它，还要记录下来：
- 这次为什么失败
- 采取了什么策略
- 策略合适吗
- 下次类似任务该调整什么

这其实就是人类的"复盘"。Agent 的成熟度，最终要看它能不能从自己的失败中学到东西，而不只是"每次都按既定策略处理"。
