## 事件还原

作者接手同事小张负责维护的表单引擎模块——一个三年迭代下来膨胀到"大几千行、单文件、无类型、命名从 data1 到 tempArr2"的代码。新需求加不进去，于是用周末时间把文件丢给 Codex：大约二十分钟得到一个拆成6个模块的重构方案，完整类型定义，测试框架。

作者又花了大半个周末逐行审查、补边界、跑通测试，周一提了大 PR。

结果：小张没说谢谢，找了领导。

领导谈话：技术上没问题，做法有问题——应该提前和原作者对齐。

## 问题根源：AI 消除了"重构的隐性成本"

这篇文章真正有价值的洞察是这一段：

> "过去，重构的成本是人人平等的。花两周重构一个模块，意味着你确实投入了时间和精力，这本身就是一种'尊重'。但 AI 把重构的成本降到了接近零。"

时间成本在工程协作中扮演了一个微妙的缓冲器角色——它让人不得不三思，不得不沟通，不得不寻求共识，因为你要付出真实的代价。当这个成本趋近于零，人们更容易越过沟通直接动手。

小张的三个抗议点都是理性的：
1. 没有提前沟通——他没参与决策
2. 感觉被否定——三年工作被 AI 二十分钟"替换"
3. 维护成本转嫁——新架构是别人设计的，但以后还是他在维护

每一点都成立。这不是情绪问题，是真实的工作边界问题。

## AI 时代协作的"效率暴力"陷阱

作者的核心反思：**"技术上正确"不等于"做法正确"**。

这个问题在 AI 编程工具普及后会越来越常见：
- 任何人都可以在几小时内生成大规模代码变更
- 生成的代码质量可能比原版更好
- 但绕过协作过程的代价是隐性的、延迟的

一个有用的思维框架：把 AI 生成的代码改动视为**大型 PR 的提案**，而不是可以直接提交的成品。大型 PR 需要设计评审、需要原作者参与、需要拆分为可审阅的小块。这些流程的存在不是官僚主义，是信任成本的分摊机制。

## 作者总结的5条备忘录

1. 想重构别人的模块 → 先和原作者讨论方案，不要直接让 AI 改完提 PR
2. AI 生成了大量改动 → 拆成多个小 PR 逐步合入
3. 发现别人代码有问题 → Code Review 中指出，不要自己 fork 过来用 AI 重写
4. 用 AI 加速开发 → 分享方法帮团队一起提效，不要一个人偷偷用制造效率差
5. AI 方案和同事方案冲突 → 作为"另一种思路"讨论，不要拿 AI 方案否定同事

## 我的判断

这篇文章的价值不在于提供了什么新技术，而在于它准确描述了一个**大多数团队还没意识到的新型冲突模式**。

最终作者采用的解决方案颇耐人寻味：放弃大 PR，拆成多个模块级别的小 PR，小张全程参与 Review，花了一周多。比"AI 二十分钟"慢了几十倍，但团队关系完好，小张在 Review 过程中熟悉了新结构。

> "有时候，慢一点才是真的快。"

这是一句值得记住的工程哲学。AI 工具提升了个人效率，但团队效率的瓶颈从来不在代码生成速度，而在认知对齐速度。
