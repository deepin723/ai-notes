## 项目信息

- **仓库**：malisper/pgrust
- **今日 Star**：774
- **语言**：Rust
- **目标**：兼容 PostgreSQL 18.3 的完整 Rust 重写版本

---

## 已达成的里程碑

pgrust 不是一个玩具项目，它的进展已经相当实质：

- **46,000+ 回归测试**：通过了 Postgres 官方完整回归测试套件的全部 46k+ 个查询（截至 README 发布）
- **磁盘兼容**：可以直接从已有的 Postgres 18.3 数据目录启动（无需迁移）
- **正在开发的新版本**（尚未公开发布）：
  - **100% 通过 Postgres 回归测试套件**
  - **线程-per-连接模型**（替代原始 Postgres 的进程-per-连接，内存效率大幅提升）
  - **事务负载：比 Postgres 快 50%**
  - **分析负载：比 Postgres 快约 300 倍**（ClickBench 上慢于 ClickHouse 2x，但有优化空间）

---

## 技术路线

作者的核心思路：用 AI 辅助编程 + Rust 类型系统，探索 Postgres 内核层的深度改造。

Postgres 的原始架构（C 语言，几十年积累）有几个难改的地方：
1. **进程模型**：每个连接一个 Unix 进程，开销极大，连接数上去就内存压力大
2. **执行器**：火山模型（Volcano/Iterator），行级拉取，在 OLAP 场景效率差
3. **代码安全性**：C 语言的内存不安全带来漏洞风险

Rust 重写让这三个问题都有机会系统性解决——特别是线程模型切换，是对原始设计的根本性重构。

---

## 为什么值得关注

数据库底层能 300x 快于 Postgres 的分析查询，这个数字非常激进，但有理由相信它的分析路径是靠谱的：

- ClickBench 基准（分析型负载）是公认的可信参考
- "2x slower than ClickHouse"说明它已经进入列存/向量化执行的数量级，和 Postgres 根本不在一个数量级

这个项目的意义不在于"要替代 Postgres"，而在于证明了一条路：**用 AI 辅助下的 Rust 重写可以在保持兼容性的同时实现数量级性能提升**。

---

## 我的判断

pgrust 现在还不 production-ready，作者也坦诚这一点。但它展示的方向和方法论值得认真对待：

- **AI 辅助编程的最佳用场之一就是这类"规则确定、目标明确"的重写任务**——有 Postgres 官方测试套件做 oracle，每一步进展都可以量化验证
- **内存数据库 vs 磁盘数据库**的分野正在被模糊，Rust 的零成本抽象使得"又快又安全"不再是矛盾
- 如果新版本的 300x 分析性能被独立复现，会成为数据库领域的重大新闻

**风险**：作者目前是独立开发者，Postgres 的维护历史有超过 35 年，追上生产级可靠性需要的不只是代码，还有社区和长时间的打磨。
