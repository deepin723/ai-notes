会写 HTML、CSS 和 JavaScript，已经拥有理解这款游戏的基础。接下来需要补的是：如何让一份 JavaScript 状态在时间中连续变化，再把它绘制出来。

本系列以 2026-09-15 的项目代码为依据，重点复盘四名角色的网页实现，不是通用游戏设计大纲，也不是 Unity 教程。读完应能自己完成：加载图片 → 播放动作 → WASD 移动 → 鼠标攻击 → 判断命中 → 播放反馈 → 升级选牌。

## 一、先分清楚我们到底做了什么

现有四角色试玩入口在游戏项目的 `reports/two-hero-growth-20260914/play/`。目录名称保留历史日期，目前已包含小焰、紫魇、幽灯和脉冲机兵。项目根目录旧游戏、各角色独立 demo、这个成长关卡是不同入口，阅读时不能把它们的机制混在一起。

这版浏览器运行时主要使用：

| 任务 | 实际使用的技术 | 前端类比 |
| --- | --- | --- |
| 页面结构、技能按钮、选卡弹层 | HTML 与 DOM | 常规业务页面 |
| 布局、面板、字体与响应式 | CSS | Flex/Grid 布局 |
| 战场、角色、子弹与特效 | Canvas 2D | 每帧重绘的一张画布 |
| 玩家、敌人、技能和成长状态 | 原生 JavaScript、ES Modules | 拆成模块的业务状态 |
| 浏览器帧调度 | requestAnimationFrame | 一个持续执行的刷新回调 |
| 短音效播放和混音 | Web Audio API | 可编排的声音节点图 |
| Unity 素材离线解析 | Python、UnityPy | 构建阶段的数据转换工具 |
| 图像整理与图集打包 | Pillow | 图片构建管线 |
| 资源索引与查询 | SQLite | 离线资产数据库 |

我们没有把原游戏 C# 逻辑直接跑在浏览器里，也没有在这几个角色 demo 中嵌入 Unity WebGL。浏览器拿到的是处理好的 PNG、JSON、声音文件和我们自己写的游戏逻辑。离线 Python 工具不用跟着每一名玩家运行。

尤其要区别“来源动作”和“玩家机制”：原素材提供角色怎么动；我们的代码决定什么时候能动、打谁、伤害是多少、能不能取消、怎样升级。狼人等角色来自敌人动画，改造成玩家后的技能关系是重新设计的。

## 二、一帧里到底发生什么

可以把循环理解成下面这条数据流：

```text
键盘与鼠标 → 输入状态
                 ↓
游戏 step(dt)：位置、动作时间、弹体、碰撞、冷却
                 ↓
伤害与事件：命中、击杀、经验、声音、视觉反馈
                 ↓
render()：背景 → 角色/敌人 → 弹体/特效 → 战斗标记
                 ↓
浏览器下一次 requestAnimationFrame
```

这里最重要的拆分是 `update` 与 `render`。前者改变游戏世界，后者读取世界并绘制。尽量不要在画一个敌人的时候顺便扣血，也不要因为浏览器多绘制一次就多发一颗子弹。

教学结构如下，不是现有文件的逐字拷贝：

```js
function update(dt) {
  readMovement(dt);
  updateActions(dt);
  updateProjectiles(dt);
  resolveContacts();
  updateFeedback(dt);
}

function render() {
  drawBackground();
  drawActors();
  drawProjectiles();
  drawFeedback();
}
```

这些函数名表示职责，不能单独复制运行；第 03 篇提供一份完整可运行的小实验。

## 三、动画不是一个不停换 src 的 img 吗

最简单的逐帧动画确实可以这样理解，但我们的角色比这个复杂。

小焰可能同时包含前腿、后腿、披风、身体、武器和阴影。每个部件有自己的关键帧与坐标。当前时间为 0.17 秒时，需要先选出每个部件对应的图片，再按层级叠起来。机兵还要处理父子节点变换和独立双臂。

因此动画播放器其实在回答三个问题：

1. 当前播放哪个动作，例如 `Run_E` 或 `RollAtk_E`？
2. 这个动作播放到几秒，每条轨道此刻选哪张图片？
3. 图片相对角色原点画在哪里，旋转、缩放和前后关系怎样？

帧画得精美只解决了其中一部分。脚底锚点错了会抖，时间轴错了会卡，重复画了一层身体会重影。许多“动画不好看”最后是坐标、采样或状态衔接问题。

## 四、为什么没有把每个怪物做成一个 DOM 元素

DOM 很适合面板与按钮，能自然获得排版、焦点和可访问性。战场则需要大量连续移动、裁图和自定义绘制。当前项目选择 Canvas 集中绘制战场，再用 DOM 做升级选卡和控制面板。

这不是说 DOM 一定慢、Canvas 一定快。Canvas 每次重绘也有成本；如果把每张图片反复解码、每帧创建临时画布，一样会卡。选择应来自对象数量、效果需求和测量，而不是技术标签。

同理，Vue/React 可以管理角色选择、背包和设置，但不必让每颗子弹的位置都进入响应式更新。游戏世界可以是普通对象，界面只在必要时更新摘要。

## 七、第一步练习

先用一个方块代表玩家，不用任何素材：按 D 时让 `player.x` 逐渐增大，松开停止。然后增加一个会循环变化的数字，代表动画帧号。把“位置时间”和“动画时间”都看见后，再加载真实素材。
