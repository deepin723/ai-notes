> 为什么 Rust 有 `rustc` 了还要一个 `rust-analyzer`？两者都"懂" Rust，但定位完全不同。属于 [[note_1784477841000_ra_overview]] 的延伸。

## 一、一表看清差别

| 维度 | rustc | rust-analyzer |
|------|-------|---------------|
| 身份 | 编译器 | IDE 语言服务（LSP server） |
| 首要目标 | 生成正确的可执行文件/库 | 给编辑器实时反馈 |
| 速度取向 | 慢一点没关系，要**全且准** | 必须**毫秒级**，可以不够准 |
| 输入 | 假设代码基本完整正确 | 代码可能残缺、有语法错误 |
| borrow checker | 全套跑（lifetime、NLL、Polonius 等） | 部分跑或不跑（太慢，IDE 不需要那么严） |
| 计算模式 | 一次性全量（每次 `cargo build` 从头） | 增量（只算改的，见 [[note_1784477842000_ra_salsa]]） |
| 宏展开 | 必须、完整 | 尽量，过程宏靠 proc-macro srv 兜底 |
| 诊断 | **权威** | **提示性**，可能和 rustc 对不上 |
| 是否产出二进制 | 是 | 否 |

## 二、为什么不能合并成一套

理论上最理想是"rustc 既当编译器又当 IDE 后端"，但历史和工程约束让它们分家：

**1. 速度模型不兼容。** rustc 的设计是"一次跑完整管线"，加大量缓存（增量编译）来避免重复，但单文件改动仍可能触发几十秒重算。r-a 靠 Salsa 的细粒度依赖追踪，能对一个按键做到毫秒响应。这是**架构**差异，不是调参能弥合的。

**2. 容错要求相反。** rustc 遇到错误**就该**停下来报错（编译器职责）；r-a 必须**继续**给出部分结果（IDE 职责，见 [[note_1784477843000_ra_syntax_tree]] 的容错 parser）。两种错误处理策略很难塞进同一个管线。

**3. borrow checker 太重。** borrow check 是 Rust 编译最贵的部分之一，但它对 IDE（补全、跳转）几乎没价值——你打 `.` 要的是方法列表，不是"这段代码有没有违反借用规则"。r-a 主动跳过它换速度。

## 三、r-a 不够准怎么办：flycheck 兜底

正因为 r-a 自己的类型/借用检查不完整，它的诊断**会漏、会错**。所以 r-a 做了个补救：**flycheck**——在后台起一个 `cargo check` 子进程，把 rustc 的真诊断也拉进来展示。

你在 VSCode 里看到的红波浪线其实分两个来源：

```
红波浪线
  ├─ 来自 r-a 自己推断（快，但不全准）
  └─ 来自 cargo check / rustc（慢，但权威）
```

r-a 的红线立刻出，rustc 的红线晚一点但更可信。**两者不一致时，以 cargo check 为准。** 这是日常开发的一个实务经验。

## 四、两套代码的"重复"代价

r-a 自己实现了一套 HIR + 类型推断 + 宏展开，和 rustc 里那套**不完全一致**。这是公认的"双倍维护"痛：

- rustc 修了个类型推断 bug，r-a 不一定同步跟；
- r-a 对某些语法的理解可能落后 rustc；
- 用户体感："为什么 `cargo build` 过了，IDE 还报红？" → 来源就是这个错位。

## 五、未来：在融合

rustc 团队和 r-a 团队一直在推进**共享底层**，避免两套：

- **rustc 的 query 系统**：rustc 内部也有类似 Salsa 的查询化架构（基于 `rustc_query_system`），目标之一就是未来让 IDE 能直接复用 rustc 的查询，而不是 r-a 自己实现一遍。
- **HIR / Ty 维度统一**：让 rustc 的中间表示对 IDE 友好，r-a 能"蹭" rustc 的真类型推断。
- r-a 已是官方项目（rust-lang 组织），不再是纯社区第三方。

完全融合是个多年工程，目前（2026）还是"两套并行、flycheck 兜底"的状态。

## 六、对日常开发的实务结论

1. **IDE 报错别全信**：r-a 的红线是"大概有问题"，要看 cargo check 那批才权威。
2. **CI / 提交前一定 `cargo check`（或 `cargo clippy`）**：r-a 漏掉的问题靠这步兜住。
3. **r-a 卡或诊断乱了**：保存所有文件后等一次 flycheck 跑完，红波浪线会被 rustc 的结果修正回来。
4. **想要"准"去查 rustc 文档/rustc 错误码**：`E0xxx` 那套错误码是 rustc 的，r-a 诊断里引用它就是借 rustc 的口径。

## 七、和 OpenCut 的关联

这次装 OpenCut desktop（[[note_1784477847000_opencut_desktop]]）时，`cargo build` 失败在 Metal shader，那一步就是**真·rustc 编译管线**在跑（不是 r-a）。r-a 平时在 VSCode 里给你画红线；一旦 `cargo build`/`check`，rustc 才上场干真活。两者在你日常里**同时存在、分工协作**，这篇把分工讲清楚了。

## 八、一句话总结

rustc 管对、r-a 管快——一个是一次性全量、严格、权威的编译器，一个是增量、容错、提示性的 IDE 服务。r-a 不够准的地方靠后台 flycheck 跑 rustc 兜底。两者不一致时，以 cargo check 为准。
