## 这个项目要挑战什么

主流 RAG 的经典流程：
1. 把长文档切成 chunks
2. 每个 chunk 生成 embedding
3. 存到向量数据库（Pinecone / Weaviate / Milvus / Chroma）
4. 用户问题转 embedding
5. **相似度最近的 k 个 chunks** → 塞到 LLM context

PageIndex 的作者提出一个**反直觉的核心问题**：

> **相似性 ≠ 相关性。**
>
> 传统向量 RAG 基于语义相似度（semantic similarity）。但我们真正需要的是相关性（relevance），而相关性需要**推理**。
>
> 专业文档里的检索，相似度匹配经常失效。

---

## PageIndex 怎么做

### 核心思路：建树，不建向量

灵感来自 AlphaGo：
> 用层级树索引（hierarchical tree index）组织长文档，用 LLM 在树上**推理**，做 agentic、context-aware 的检索。
> 模拟人类专家"翻书"的方式。

具体流程：
1. 把长文档（比如 500 页 PDF）**预处理成层级树**
   - 章节 → 节 → 段落 的结构
2. 用户提问时，**LLM 沿着树导航**
   - "这个问题可能在哪一章？" → 选章
   - "章里哪一节？" → 选节
   - "节里哪一段？" → 读取返回

这很像人类研究员查书的方式——**看目录定位，不是扫描全文找"最像"的**。

### 相比传统 RAG 的差别

| 维度 | 向量 RAG | PageIndex |
|------|---------|-----------|
| 预处理 | Chunk + embedding | 建树（保留章节结构）|
| 存储 | 向量数据库 | 树（JSON/SQLite 就行）|
| 检索 | 向量相似度 top-k | **LLM 推理导航** |
| 上下文感知 | 弱（每个 chunk 独立）| **强（树路径提供上下文）**|
| 运维成本 | 向量 DB 本身 | 近 0 |
| 对 "结构化文档" 的效果 | 一般 | 好 |
| 对 "纯 free text" 的效果 | 好 | 一般 |

## 为什么这是有意义的挑战

### 向量 RAG 有几个长期没解决的问题

**① Chunk size 的玄学**

Chunk 太大 → 检索粒度粗，准确率低。
Chunk 太小 → 丢失上下文，LLM 看不懂。

这个参数没有**原则性的"正确值"**，只能靠各种启发式（滑动窗口、按段落、按标点…）。

**② 语义接近 ≠ 信息相关**

用户问"这家公司 2023 年的净利润是多少"。
向量检索可能返回**谈论 2023 年其他数据**的段落（它们跟问题"语义接近"），而不是真正包含净利润的段落。

**③ 结构化文档的层级信息被拍平**

一个法律文档的**"第 5 章第 3 节"** 跟 **"第 8 章第 1 节"** 在向量空间里可能离得很近（因为都是法律语言）。但它们在逻辑上差一个大山。

向量 RAG 把所有东西拍成一个平面。**PageIndex 保留了层级结构**。

### PageIndex 在哪些场景应该比向量 RAG 好

- **长的结构化文档**（法律合同、科研论文、招股书、产品手册）
- **需要多步推理的问题**（"先找第 5 章的定义，再到第 12 章看它的应用")
- **上下文依赖强的检索**（"这个条款的例外在哪里？"）

### 向量 RAG 可能还是更好的场景

- **海量短文档**（微博、评论、邮件）
- **语义模糊的查询**（用户问得很随意）
- **多语言混合检索**
- **低延迟要求**（向量检索 1ms 返回，PageIndex 需要 LLM 推理几秒）

**两种方法是互补的，不是替代。**

## 我的判断

### ① Vectorless RAG 是对 2023-2024 "RAG = 向量数据库" 路径的重要挑战

过去两年所有 AI 教程、创业公司都默认 "RAG 等于向量 DB"。这种路径依赖变成了**思维定势**。

PageIndex 不是第一个反思向量 RAG 的（Microsoft 的 GraphRAG、各种 hybrid 方案都在做），但它**把观点表述得最清楚**："相似性不等于相关性"。这句话会成为很多人的顿悟时刻。

### ② LLM 越便宜、越快，"推理型检索" 越可行

过去做"用 LLM 推理来导航"太贵：
- GPT-4 一次调用 0.01 美元
- 导航一个 500 页文档需要 10-20 次推理 = 每次查询 0.1-0.2 美元
- 不合算

**现在不一样了**：
- GPT-5 nano、Claude Haiku、DeepSeek V3 这类模型每次推理 0.0001 美元级
- 导航成本掉到了 0.001-0.002 美元级
- 跟向量 DB 的检索 + 托管成本相当

**"用 LLM 换 embedding"的经济可行性**最近 6 个月刚变好。PageIndex 是抓住了这个时间窗。

### ③ 这类"非主流"架构在特定场景会形成细分优势

我不相信 PageIndex 会完全取代向量 RAG。但：
- **法律 AI** 可能会主要用 PageIndex 类方案（法律文件结构化强）
- **医学文献 AI** 可能会混用（既有结构又有自由文本）
- **财报分析** 肯定偏向 PageIndex（pitchbook、10-K 格式很规范）

**2026 年底前**，我们会看到至少 3-5 家创业公司在特定领域主打"PageIndex 架构"。

## 对我的启示

### 技术层面

1. **如果我要做 RAG 系统**，不要无脑上向量 DB。先判断文档结构化程度：
   - **高结构化**（法律、学术、财报）→ 试试 PageIndex 类方法
   - **低结构化 + 大规模**（聊天记录、文档库）→ 向量 RAG 还是对的
   - **中间态** → 混合

2. **Vectorless 思路不只 RAG 能用**。搜索排序、推荐系统也可以反思："我是真的要语义相似，还是用户真的要的是逻辑相关？"

3. **树形索引 + LLM 推理** 这个 pattern 可以迁移到其他场景：
   - 大型代码库导航（比按文件 embedding 搜要好）
   - 大型 SQL 数据库的 schema 理解
   - 企业内部 wiki 检索

### 更深的一层

**技术路径的"主流化"往往伴随着隐性的约束假设**。向量 RAG 流行让我们默认"检索 = 相似度匹配"，但这个默认正在被挑战。

类似的反思适用于：
- "AI 记忆 = vector DB 存对话" ← 可能是错的，长期记忆需要结构化而非向量化
- "多模态 = 把图片 embedding 成文本空间" ← 可能是错的，要用原生视觉推理
- "Agent 规划 = LLM 生成 JSON tree" ← 可能是错的，有更好的结构化规划方法

**当一个技术方案成为业界标配，警惕这个标配的隐性假设**。
