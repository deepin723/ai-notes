动画播放器负责“这个动作现在画哪一帧”，控制器负责“这时是否允许开始这个动作”。角色卡手、按键失效、连招被打断，大多需要从第二层排查。

## 一、输入是意图，不是动画

按下 A 不应该直接调用 `drawAttackFrame()`，而应该向游戏提出“开始普通攻击”的请求。游戏检查暂停、当前动作、冷却、弹药等状态，决定立即执行、缓存到衔接点，还是拒绝。

移动键和技能键的语义也不同：

- WASD 是持续状态：只要还按住，就持续产生移动意图。
- Q/E 是一次性触发：操作系统的自动重复 keydown 不能让技能重复排队。
- 按住鼠标开火是持续意图，但每一轮射击仍由动作时间轴决定。

## 二、为什么要优先使用 event.code

中文输入法、键盘布局和焦点变化，都会影响 `event.key`。当前小焰 `input.mjs` 先映射 `KeyW/KeyA/.../Space` 等物理键码，再把它们转换成游戏自己的小写键名。

输入框和快捷键组合应交给正常页面操作；而在 Checkbox 等控件获得焦点时，游戏移动又不应该轻易丢失。源码针对输入目标做了区分。keydown 与 keyup 的目标还可能不同，因此松键清理不能完全照搬按键时的过滤逻辑。

最小教学实现：

```js
const held = new Set();
window.addEventListener('keydown', event => {
  if (!['KeyW', 'KeyA', 'KeyS', 'KeyD'].includes(event.code)) return;
  held.add(event.code);
});
window.addEventListener('keyup', event => held.delete(event.code));
window.addEventListener('blur', () => held.clear());
```

这还不是项目完整输入模块：未处理文本编辑、相反键优先级、暂停和鼠标捕获。教学代码先展示“记录状态而非按一下移动一下”的核心。

## 三、靠墙后反向移动为何容易出问题

用户曾反馈：角色到最右侧后，按左不能回来，要再按一次右才恢复。这个现象提示要查输入状态与冲突处理，而不能仅仅扩大地图边界。

当前小焰模块利用 Set 的插入顺序实现“最新实际按下的相反方向优先”。新按键先删除再添加；自动重复不会重新抢走优先级。`movementAxis()` 按插入顺序遍历，所以后出现的左右键覆盖先出现的方向。

```js
// 摘录核心规则，held 保存的是游戏键名。
if (movement && !event.repeat) held.delete(key);
if (movement || trigger) held.add(key);
```

碰到边界只限制位置，不应偷偷修改玩家的 held 状态。否则物理按键还按着，程序却认为松开，二者就会不同步。也不能把所有“移动失效”都归为同一原因；还要观察角色是否仍能攻击、是否被动作锁定、是否失焦。

## 四、鼠标坐标要从页面换算到战场

画布逻辑宽度是 1200，但 CSS 可能把它显示成 900。不能把 `clientX` 直接作为游戏坐标。

```js
const r = canvas.getBoundingClientRect();
pointer.x = (event.clientX - r.left) * WORLD_W / r.width;
pointer.y = (event.clientY - r.top) * WORLD_H / r.height;
const angle = Math.atan2(pointer.y - muzzle.y, pointer.x - muzzle.x);
```

这个公式假定画布没有额外的内部留白或复杂旋转；若采用相机视口与 letterbox，还要扣除视口偏移。`atan2` 给角度，`cos/sin` 给弹体方向。人物八方向图可以离散，弹道不必只有八方向。

## 五、动作状态机其实就是普通对象与条件转换

机兵当前的动作对象保存 `kind/stage/t/age/dir/angle/spec`。Q 的 `spec` 是三段原动画：TripleShotDash 的 Intro、Loop、Outro。`stage` 表示当前段，`t` 是段内时间。

```text
Idle
  → Basic Intro → Basic Loop → Basic Outro → Idle
                     ↑   │
                     └───┘ 持续按住时重复发射段

Q 请求 → Dash Intro → Dash Loop（位移与齐射）→ Dash Outro
```

不用一开始就引入状态机库。只要明确“状态有哪些、谁能进入、何时结束、结束后去哪里”，普通 JS 就足够描述目前规模。复杂到多层并行状态互相冲突时，再评估更规范的状态图或工具。

## 六、缓存输入与取消动作不是一回事

当前机兵在普通攻击时接受技能请求：不在发射循环段时可以立即转技能，在发射段则缓存，等当前轮结束再衔接。按住普攻时不必每轮重新播放完整开场，因此可以减少连续射击的卡顿感。

幽灯则会把普攻期间的 Q/E/位移请求缓存到普攻结束；这会产生可预测但仍然存在的等待。两角色处理不同，不能以“都叫 Q”就用同一套取消规则。

设计新的取消窗口时，要画出时间线，例如：

```text
0.00 开始准备 ─ 0.12 接触前 ─ 0.20 命中 ─ 0.32 可接技能 ─ 0.48 完成
```

以上数字是教学设想。若接触前取消，不应照常扣血；接触后取消，不应再次触发同一轮命中。仅仅把动作持续时间缩短，很容易破坏这两个约束。

## 七、被动按出手算，还是按命中算

这是狼人迭代里非常重要的分歧。用户要的是挥完完整三爪后接两次强化爪，空挥也推进。若在 `hitEnemy()` 内累加，打到三只怪就会错误算成挥了三次。

正确做法是为不同事件建不同计数：

| 事件 | 可以驱动什么 |
| --- | --- |
| 发射一轮普攻 | 机兵第五轮弹仓共振 |
| 普攻动作完成 | 幽灯每四次普攻生灯 |
| 爪击进入对应接触段 | 狼人完整连爪推进 |
| 命中一个不同敌人 | 吸血、命中触发、目标数奖励 |
| 击杀 | 掉经验、击杀充能 |

同一次普攻能产生多个 hit，但只能产生一个符合定义的 attack/volley 事件。反过来，被取消且没完成的攻击应不应该计数，必须由具体被动说明决定，不能全部共用一个计数器。

## 八、连招资源存在，不等于连招机制存在

小焰当前真实情况是：炎剑有八方向 `RollAtk`，右键会进入它；翻滚结束后左键仍进入普通攻击。S5 的“翻身回锋”增加后续范围和护盾，并没有自动把普通攻击换成 `RollAtk`。

这正好解释了前端接入动画时经常遇到的差距：文件加载成功，只证明资源可用；还必须做输入窗口、动作分支、方向、命中时刻和连段计数。

“普攻一 → 翻滚突进斩 → 普攻二”是下一步可讨论的目标，截至本文核查并未接入，不应在学习文档里冒充已完成实现。

## 九、这一层怎样测试

以步骤测试行为：先按右 → 新按左 → 松右，应继续向左；失焦后 held 清空；按住普攻十轮只触发两次第五轮被动；Q 在不同阶段请求得到预期的立即/缓存结果；暂停期间动作时间与冷却不变。

源码阅读点：小焰 `input.mjs`、正式关卡 `ember.mjs`；机兵 `engine.mjs` 的 `request()` 和 `step()`；幽灯 `engine.mjs` 的 `completeBasic()`；狼人 `engine.mjs` 的动作阶段推进。上述规则比单纯“按键后截一张图”更容易发现逻辑错误。
