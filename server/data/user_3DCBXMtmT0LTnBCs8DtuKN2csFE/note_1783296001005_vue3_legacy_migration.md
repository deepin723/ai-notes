## 遗留系统的经典画像

2016年上线的后台管理系统：jQuery 1.12 + Bootstrap 3 + 手写模板引擎，8万行代码，HTML 里 `<script>` 直接引入30多个 JS 文件，加载顺序靠人工记忆。核心 app.js 文件6000多行，DOM操作、AJAX请求、业务逻辑、工具函数全部混在一起。

一行神奇注释：`// 2018.3.15 老王加的，别删，删了报表页面崩`——老王已于2019年离职。

最终压垮骆驼的是一次事故：加一个批量导出按钮，改了3行代码，全站样式崩溃。原因是全局变量 `i` 命名冲突，排查4小时。

## 核心策略：渐进式入侵

不做"一刀切重写"，而是三条原则并行：

1. **页面级替换**：一次只重构一个页面，不碰其他页面
2. **路由劫持**：Vue Router 接管部分路由，jQuery 和 Vue 页面共存
3. **数据层复用**：Vue 组件直接调用现有的 jQuery AJAX 封装，后端接口零改动

## 技术实现要点

**代码隔离**：在项目根目录新建 `vue-app/` 文件夹，用 Vite 初始化 Vue3 项目。HTML 里加 `#vue-app` 挂载点（默认隐藏），`main.js` 里通过路由映射表判断当前路径走 Vue 还是 jQuery。两套系统在同一个 HTML 文件里共存，互不感知。

**适配层**：写 `legacyApi.js`，直接调用 `window.LegacyAPI`（公司用了8年的 jQuery AJAX 封装）。Vue 组件通过此适配层调用接口，后端、接口文档、测试代码全部零改动。

**Web Components 桥接**：用 `defineCustomElement` 把 Vue 组件封装为原生 Web Components（如 `<order-table>`），在未迁移的 jQuery 页面里直接当普通 HTML 标签使用。jQuery 负责页面框架，Vue 负责复杂交互组件，两者可以混搭。

## 遇到的坑

| 问题 | 原因 | 解法 |
|---|---|---|
| 全局样式污染 | Bootstrap 3 影响 Vue 组件内部样式 | scoped 样式 + CSS Modules |
| 内存泄漏 | Vue 组件卸载时 jQuery 事件监听未清理 | onUnmounted 里手动 $.off() |
| 路由刷新问题 | history 模式需服务端支持通配符 | 改用 hash 模式 |
| 首屏体积超重 | Vue3 + Element Plus 打包超 400KB | manualChunks 拆包 + CDN，降至 200KB |

## 结果

三个月后，Vue3 页面占项目60%的访问量。团队6人中4人开始主动用 Vue3 写新页面——没有行政命令，纯靠"好用"的自然传播。CTO 主动提出："要不把剩下的也迁了？" 此时作者才拿出完整迁移方案。

## 我的判断

这个案例展示的是一种**自下而上的技术债治理路径**。不申请专项排期，不说服管理层，而是在日常需求开发的间隙悄悄替换——本质上是把"技术改进"和"业务需求"捆绑在一起，让改进有了实际的业务外壳。

这种方式的前提条件：
- 系统痛点已经影响到正常需求速度（否则没有动力）
- 迁移可以页面级隔离，不影响其他页面（否则风险太大）
- 有适配层可以复用现有数据层（否则工作量倍增）

反直觉的点：**最难的部分不是技术方案，而是"不惊动管理层"的悄悄执行**。作者的时间管理策略是：利用需求间隙，每次重构一个页面，上线一个页面，积累口碑。等到管理层发现时，60%的迁移已经完成，此时推动剩余迁移阻力最小。

对我的启示：在资源有限的环境里推动技术改进，最有效的方式往往是"把技术目标包装进业务目标"，每次迁移都要有一个看得见的功能改善（比如那个变快的订单页面），而不只是"代码变好了"。
