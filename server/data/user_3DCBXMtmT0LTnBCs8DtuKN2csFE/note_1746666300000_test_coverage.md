## 核心观点（一句话）

> **覆盖率 100% 不是质量指标，是心理安慰。真正有用的测试不是"覆盖多少代码行"，是"能不能发现重要 bug"。**

---

## 作者的测试金字塔拆法

经典的金字塔模型，但作者给出了**对每一层"适合测 vs 不适合测"的具体清单**，这是我最喜欢的部分：

### 单元测试（70%）

**适合测**：
- 纯函数（输入输出确定、无副作用）
- 业务规则（`calculateDiscount(price, level)`）
- 工具函数（`formatDate`、`parseQuery`）

**不适合测**（测了也白测）：
- ❌ 框架内部逻辑（React setState、Vue 响应式——那是框架的事）
- ❌ 简单的 getter/setter
- ❌ 常量定义

**黄金法则**：
> **如果重构代码不破坏测试，说明你测的是行为，不是实现。**

这句话我想裱起来。大部分前端测试写挂掉是因为测了 CSS 类名、DOM 结构、内部 state——这些重构就会变化的东西。

### 组件测试（20%）

**适合测**：
- 根据 props 渲染正确的内容
- 点击按钮触发正确回调
- 表单输入后数据变化
- 异步加载显示 loading 状态

**不适合测**：
- ❌ CSS 样式（视觉回归测试的事）
- ❌ 内部 state 的具体值
- ❌ 第三方 UI 库的行为（假设它没问题）

### E2E 测试（10%）

**适合测**（只写 3-5 个核心流程）：
- 登录 → 访问个人主页 → 修改头像
- 搜索 → 加入购物车 → 结算 → 支付成功
- 未登录访问受保护页面 → 跳转登录页

**不适合测**：
- ❌ 每个细节（按钮悬浮效果）
- ❌ 容易变化的面包屑导航
- ❌ 第三方依赖的页面

**维护技巧**：给关键元素加 `data-cy` 属性，避免改样式或文本时测试挂掉。

## 覆盖率的谎言

这段是整篇文章最精髓的地方。

> 很多团队追求 100% 覆盖率，结果工程师花大量时间测无关紧要的代码（比如测 Redux 的 action creator 是个纯对象）。
>
> 覆盖率工具（Istanbul）只能告诉你「哪些代码没执行过」，不能告诉你「没测到的重要逻辑」。
>
> 有时 100% 覆盖率，却漏掉了一个关键的空值判断。

### 作者给的正确标准

- 核心业务逻辑达 **80%** 就行
- UI 组件覆盖率参考即可
- 关注**未覆盖的重要代码**，而不是数字

## 我的判断

### ① "100% 覆盖率" 这个指标是 KPI 化思维在工程上的失败

覆盖率这个指标好量化，好考核，好显示在大屏上。于是管理者自然追求它。

但**好量化的指标未必是好指标**。Goodhart's Law：
> **当一个指标成为目标，它就不再是一个好指标。**

90% 覆盖率 + 覆盖的都是核心业务 > 100% 覆盖率 + 测了一堆 getter。

### ② 前端测试有一个特殊困境：UI 变化太快

后端代码相对稳定，一个 API 逻辑写好后可能几年不变。前端不一样——UI 每季度都改版。

这意味着：**前端测试的 ROI（投入产出比）比后端低**。同样写一个测试，后端可能管 3 年，前端可能管 3 个月。

所以前端测试策略要更"精打细算"：
- **业务逻辑**（折扣计算、表单校验）重测——这部分稳定
- **UI 组件**轻测——用法稳定就行，不测内部
- **E2E** 只测核心路径——其他改 UI 时必挂

### ③ "重构不破坏测试"是判断测试是否正确的北极星指标

如果你的测试经常因为重构而挂，不是重构的错，是测试本身写得错——测了实现细节，没测行为。

**实操方法**：写完测试后，问自己：
- 如果我把这个函数从 class 改成 function，测试还过吗？
- 如果我把这个状态从 Redux 迁到 Zustand，测试还过吗？
- 如果我把这个 UI 从 Vue 重写成 React，测试还过吗？

**"能过"的测试是好测试**（测的是业务行为）。
**"必挂"的测试是坏测试**（测的是实现细节）。

## 对我的启示

### 实操上我立刻能用的三条

1. **不要追求覆盖率数字**。先把覆盖率工具当**诊断工具**（哪里没测），不是当**考核工具**（必须到 90%）。
2. **E2E 用 data-cy 选择器**，永远不要用 CSS 类名或文本 selector。这一个小习惯能把 E2E 的维护成本降 80%。
3. **给"核心业务逻辑模块"划一条清晰边界**，只在这条边界内追求覆盖率。UI、工具类、配置都不算核心。

### 更深的一层反思

**质量保障的底层矛盾**：人总想通过量化指标来管理质量。但质量本质上是个**定性概念**，强行量化就会扭曲。

同样的道理在：
- 用 LOC（代码行数）衡量工程产出 → 鼓励写臃肿代码
- 用 Bug 数量衡量 QA 绩效 → 鼓励开细碎 Bug
- 用商品评分衡量商家 → 刷单产业
- 用论文引用数衡量学者 → 引用互换圈

**好指标 = 量化的 + 跟真实目标相关的 + 难以造假的**。满足三条才用。100% 覆盖率只满足"量化"这一条，所以不是好指标。

## 一个反直觉的延伸

**有时候"一个测试都没写"比"为了凑覆盖率写一堆烂测试"好**。

为什么？因为：
- 烂测试**给人虚假的安全感**（"我测过了" → 不深入思考）
- 烂测试**维护成本极高**（UI 改动 → 测试挂 → 花时间修 → 但根本没发现真 bug）
- 烂测试**会被同事误解为"这块代码有保证"**，导致改动时不够小心

**不写测试**反而让人**更谨慎**。

这不是鼓励不写测试，是说：**测试应该是用来抓重要 bug 的武器，不是用来盖"我很专业"印章的道具**。
