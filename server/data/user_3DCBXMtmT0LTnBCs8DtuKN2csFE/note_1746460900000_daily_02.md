## 先说清楚 KV Cache 在解决什么问题

Transformer 做推理时，每生成一个 token，就要对之前所有 token 做一遍 attention 计算。上下文 1000 个 token，就要算 1000 次；100000 个 token，算 100000 次。这是平方复杂度，上下文越长，算力消耗越恐怖。

KV Cache 的思路非常直觉：**你上次算过的 Key/Value，直接缓存，下次直接读**。不重复算，复杂度从 O(n²) 降到 O(n)。

这不是新技术，早在 GPT-3 时代就有了。DeepSeek 厉害的地方不是发明了 KV Cache，而是把命中率做到了 **98%**，也就是说每 100 个请求，有 98 个不需要重新算，直接读缓存。

---

## 98% 怎么做到的？

### 前缀哈希复用（Prefix Hashing）

核心思路是：如果多个请求的 prompt 前缀一样（比如大量用户都用了相同的 system prompt），那这段前缀的 KV 只算一次，所有请求复用同一份缓存。

这在实际场景里很常见——绝大多数 API 调用者都有固定的 system prompt，DeepSeek 把这个规律变成了系统设计的核心假设。

### 分层存储（像 CPU 的缓存层级一样）

- 显存（L1）：最热的请求，响应延迟最低
- CPU 内存（L2）：次热数据
- NVMe SSD（L3）：冷数据，需要时加载

这套设计和 CPU 的 L1/L2/L3 cache 思路如出一辙，差别在于"命中"的代价不同，显存到 SSD 的延迟差了几个数量级。

### 预计算 + 持久化

对于高频出现的 prompt pattern，提前算好 KV 并持久化存储，类似 CDN 的预热逻辑。

## 我觉得更有价值的是背后的商业逻辑

KV Cache 命中率 98%，翻译成商业语言是：**DeepSeek 的边际成本趋近于存储成本，而不是计算成本**。

对比一下：
- 没有缓存优化：每个请求都要算，成本随请求量线性增长
- 98% 命中率：绝大多数请求只读存储，边际成本接近零

这解释了 DeepSeek 为什么能把 API 价格压到令人发指的低——不是补贴，是工程优化真实地降低了成本结构。

反过来看，这也给了其他 LLM 厂商巨大的压力：拼 API 价格，本质是在拼工程效率，不是在拼资本补贴。

## 和 Claude 的 Prompt Cache 对比

Reddit 上有开发者对比过两套机制的差异：

| 维度 | DeepSeek | Claude |
|------|----------|--------|
| 触发方式 | 全自动，对用户透明 | 显式声明，需要开发者标记 |
| 控制粒度 | 低（不透明） | 高（精确指定哪段 cache）|
| 调试难度 | 难 | 易 |
| 对普通用户友好度 | 高 | 低 |

两种思路体现了不同的设计哲学：DeepSeek 把优化藏在系统层，用户无感；Claude 把控制权交给开发者，换来更大的灵活性。

没有谁对谁错，取决于你的用户是谁——B 端开发者偏向 Claude 那种精确控制，C 端用户偏向 DeepSeek 那种开箱即用。

## 工程上的一般性思维

KV Cache 命中率背后的思维模型：**识别重复计算，找到缓存边界，用空间换时间**。

这个思想在工程里无处不在：
- 数据库查询：建索引、Redis 缓存
- 前端：memo/useMemo、CDN 静态资源
- 函数：memoization
- 算法：动态规划（DP 表的本质就是 KV Cache）

区别只是"相同"的定义不同。大模型用的是 token 前缀的精确哈希匹配，DP 用的是子问题状态的精确等价。本质是一回事。

## 一个对我来说挺有意思的问题

如果 KV Cache 命中率无限趋近 100%，大模型推理的成本会不会最终变成接近免费的？

理论上是可能的——前提是大多数请求共享足够多的上下文前缀。但个性化对话（每个人的上下文都不同）会打破这个前提。所以最终的均衡点，可能是：**标准化任务趋于免费，个性化任务维持成本**。这对 AI 产品的定价策略是个很有意思的约束条件。
