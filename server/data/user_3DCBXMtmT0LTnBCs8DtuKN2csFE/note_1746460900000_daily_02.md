## 为什么 KV Cache 是大模型推理加速的关键

Transformer 模型每次生成 token，都要对之前所有 token 做 attention 计算。随着上下文变长，这个开销呈平方级增长。

KV Cache 的思路是：**把已经算过的 Key/Value 矩阵缓存起来，下次复用，不重复计算**。

---

## DeepSeek 的 98% 是怎么做到的

### 问题背景
普通 KV Cache 缓存在单次对话内有效，但下次新对话来了，缓存就失效了（进程/显存不同）。DeepSeek 做的是**跨请求、跨会话的全局缓存复用**。

### 核心机制

**1. 前缀哈希匹配（Prefix Hashing）**
- 把每次请求的 prompt 前缀做哈希
- 如果多个用户发了相似前缀（比如系统提示词 system prompt 一样），对应的 KV Cache 直接复用
- System prompt 的 KV 只算一次，所有请求共享

**2. 分层存储**
- L1（显存）：热 cache，延迟最低
- L2（CPU 内存）：次热数据
- L3（SSD/NVMe）：冷存储，预热时加载

**3. 激进的预计算**
- 对于高频出现的 prompt 模式，提前计算并持久化 KV
- 类似 CDN 的预缓存逻辑

### 命中 98% 意味着什么
- 98% 的请求不需要从头计算，直接读缓存
- 推理成本从 O(n²) 降至接近 O(n)
- 延迟大幅下降，吞吐量成倍提升
- 边际成本趋近于存储成本而非计算成本

## 和 Claude/GPT 对比的差异

Reddit 帖子里有开发者对比发现：Claude 的 prompt cache 更侧重**显式声明**（开发者标记哪段要 cache），而 DeepSeek 是**全自动隐式**的，对用户无感知。

两种思路的取舍：
- 显式控制：灵活，开发者可以精确指定，但需要了解机制
- 全自动：简单，但缓存策略不透明，调试困难

---

## 工程启示

KV Cache 命中率的本质是**"让相似输入复用计算结果"**，这个思想在工程里处处可见：数据库查询缓存、CDN 边缘缓存、函数记忆化（memoization）、React 的 memo/useMemo...

区别只是"相似性"的定义不同，大模型用的是 token 前缀的精确匹配。
