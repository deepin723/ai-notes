## 为什么又做一个项目管理工具

Kaneo的出发点是反对项目管理软件的功能膨胀。团队真正需要的是看清工作、分配任务和推进状态，而不是不断处理通知、按钮与复杂流程。它强调简洁界面、响应速度、自托管和MIT许可，希望工具尽量“隐形”，不迫使团队适应软件本身。

README没有用几十项功能制造声量，反而把重点放在部署和数据归属上。用户既可以使用官方云服务，也能用Docker Compose同时启动Kaneo与PostgreSQL。

## 部署方式

项目提供名为drim的一键部署CLI，负责HTTPS、数据库和服务配置；也提供标准Compose示例，包含PostgreSQL 16、健康检查、持久化volume和Kaneo容器。生产环境需要配置数据库密码、`AUTH_SECRET`与客户端URL。

更复杂的团队可以使用Helm Chart部署到Kubernetes，也能把API与Web镜像分开运行。开发环境使用pnpm monorepo流程，并特别提示CORS和环境变量是常见故障点。

## 我的判断

“少即是多”是好定位，但简洁不能只靠删功能。一个项目管理工具是否轻巧，取决于它有没有清晰的数据模型、快速搜索、稳定权限和可逆操作。否则随着用户提出报表、自动化和集成需求，产品仍会再次膨胀。

自托管同样不是免费午餐。数据库升级、邮件、备份、认证密钥和灾难恢复都需要有人负责。Kaneo适合厌倦大平台且有基础运维能力的小团队，而不是所有用户的默认选择。

## 对我的启示

评价协作工具时，可先问三个问题：新成员多久能上手、完成一次核心操作需要几步、离开平台能否完整导出数据。比功能清单更能反映长期使用成本。
