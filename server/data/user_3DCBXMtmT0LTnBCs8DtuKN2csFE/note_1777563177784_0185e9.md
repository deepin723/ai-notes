## 为什么不用 Serverless，要用 Docker 容器

这是整个部署架构中最重要的一个技术决策，直接决定了 ai-image 和 Vki 项目能不能正常运行。

---

## Serverless 的本质限制

Vercel Functions / AWS Lambda 等 Serverless 平台的工作方式：

```
请求到来
    ↓
从零冷启动一个进程（约 100-500ms）
    ↓
运行函数
    ↓
固定超时（Vercel: 10s免费/60s Pro）
    ↓
进程销毁
```

**Serverless 在我们项目里遇到的具体问题：**

### 问题 1：60s 超时限制

```javascript
// ai-image 的图像生成：
const response = await fetch(baseUrl + '/responses', {
  body: JSON.stringify({ model: 'gpt-image-2', ... }),
  signal: AbortSignal.timeout(600_000),  // 我们需要 10 分钟！
})
// 图像生成实际耗时：2-5 分钟
// Vercel 免费版：最多 10 秒
// Vercel Pro：最多 60 秒
// → 结果：请求直接被 Vercel 切断，返回 504 Gateway Timeout
```

### 问题 2：SSE 长连接中断

```javascript
// ai-chat 的 SSE 连接：
res.setHeader('Content-Type', 'text/event-stream')
res.setHeader('Connection', 'keep-alive')
// SSE 连接需要保持 5-60 秒（取决于 AI 响应速度）
// Serverless 函数不支持真正的长连接
// → 结果：流式输出无法工作，只能等 AI 全部生成完才能响应
```

### 问题 3：无文件系统持久化

```javascript
// Vki 的文件存储：
const DATA_DIR = path.join(__dirname, 'data')
fs.writeFileSync(notePath(id), content)  // 写入文件系统
// Serverless 每次调用是独立进程，写的文件下次就没了
// → 结果：创建的笔记在下次请求时消失，完全无法使用
```

### 问题 4：无进程内共享状态

```javascript
// ai-image 的任务队列：
let isProcessing = false  // 进程级全局变量
const tasks = ref<Task[]>([])  // 前端内存
// Serverless 每次请求是完全独立的进程，无法共享内存
// → 队列状态在不同请求间丢失
```

## Docker 容器的解决方案

Docker 容器是「包含完整运行环境的进程」：

```
Docker 容器（持续运行的进程）
    ├── Node.js 运行时（固定版本）
    ├── 应用代码
    ├── 依赖包（node_modules）
    ├── 文件系统（可挂载持久卷）
    └── 进程内存（可共享状态）

特性：
✓ 无超时限制（常驻进程）
✓ 支持长连接（SSE / WebSocket）
✓ 文件系统持久化（Docker Volume）
✓ 进程内全局变量
✓ 冷启动只在容器启动时（一次）
```

## Dockerfile 解析

```dockerfile
# 使用 Node.js 24 官方镜像（Alpine = 轻量级 Linux，约 50MB）
FROM node:24-alpine

# 创建工作目录
WORKDIR /app

# 先复制 package.json（利用 Docker 层缓存）
# 如果 package.json 没变，下次构建跳过 npm install
COPY package*.json ./
RUN npm ci --only=production  # --only=production 不安装 devDependencies

# 复制应用代码
COPY . .

# 声明应用监听的端口（文档性，不实际开放）
EXPOSE 3003

# 容器启动命令
CMD ["node", "index.js"]
```

**Docker 层缓存机制：**
```
FROM node:24-alpine       [缓存层 1]
WORKDIR /app              [缓存层 2]
COPY package*.json ./     [缓存层 3 - 只有 package.json 变时才失效]
RUN npm ci                [缓存层 4 - package.json 不变就直接用缓存]
COPY . .                  [每次代码变化都失效]
CMD ["node", "index.js"] [缓存层 6]
```

先复制 package.json 再复制代码的原因：让 `npm install` 这一步可以走缓存，大幅减少构建时间（从 60s → 10s）。

## Railway 平台工作原理

### 部署流程（CI/CD）

```
git push origin main
    ↓
GitHub Webhook 通知 Railway
    ↓
Railway 拉取最新代码
    ↓
docker build（执行 Dockerfile）
    ↓
构建新镜像（约 1-2 分钟）
    ↓
滚动部署：启动新容器
    ↓
健康检查通过（GET /api/health → 200）
    ↓
流量切换到新容器
    ↓
旧容器停止

总耗时：约 2-3 分钟
```

### Railway 服务配置

```
项目配置（Railway Dashboard 设置）：
├── Source: GitHub 仓库
├── Root Directory: server/（只构建后端）
├── Build Command: （自动检测 Dockerfile）
├── Start Command: node index.js
├── Environment Variables:
│   ├── PORT=3003
│   └── （其他 .env 变量在这里设置）
└── Health Check Path: /api/health
```

### 三个项目的端口映射

```
ai-chat  Railway 服务 → 内部 :3001 → 公网 https://ai-chat-xxx.up.railway.app
ai-image Railway 服务 → 内部 :3003 → 公网 https://ai-image-xxx.up.railway.app
Vki      Railway 服务 → 内部 :3004 → 公网 https://vki-xxx.up.railway.app
```

Railway 自动处理 HTTPS 证书，无需配置 Nginx 或 Let's Encrypt。

## 前端部署：Vercel CDN

### 为什么前端在 Vercel 而不是 Railway

```
Vercel 优势（静态文件托管）：
✓ 全球 CDN 边缘节点（北京/上海/东京/美东...）
✓ 静态文件零延迟（就近节点缓存）
✓ 自动 HTTPS
✓ push 自动构建（vue-tsc && vite build）
✓ 免费额度慷慨

Railway 适合（长进程服务）：
✓ SSE 长连接
✓ 文件系统
✓ 常驻进程
```

### Vercel 构建配置

```json
// client/vercel.json（ai-image 示例）
{
  "rewrites": [
    {
      "source": "/api/:path*",
      "destination": "https://ai-image-backend.up.railway.app/api/:path*"
    }
  ]
}
```

Vercel 的 `rewrites` 把 `/api/*` 请求代理转发到 Railway，效果等同于开发时 Vite 的 proxy 配置。前端代码中所有 `fetch('/api/...')` 无需修改。

## 环境变量管理

### 开发环境（.env 文件）

```bash
# server/.env（不提交到 Git！加入 .gitignore）
OPENAI_API_KEY=sk-xxx
OPENAI_BASE_URL=https://bobdong.cn/v1
PORT=3003
```

```javascript
// server/index.js
import dotenv from 'dotenv'
dotenv.config()  // 加载 .env 文件到 process.env

const PORT = process.env.PORT || 3003
```

### 生产环境（Railway Dashboard）

在 Railway 的 Variables 面板设置，Railway 把这些注入为容器的环境变量。**不需要 dotenv**，Docker 容器直接读取 process.env。

```
为什么不把 .env 打包进 Docker 镜像？
→ 安全风险：镜像可能被分享/泄露
→ 灵活性：更换 API Key 不需要重新构建镜像
→ 最佳实践：配置与代码分离（12-Factor App 原则）
```

## 完整前后端部署架构图

```
开发者
  │ git push
  ↓
GitHub 仓库
  │
  ├──→ Vercel（监听 client/ 目录变化）
  │       │ vue-tsc && vite build
  │       ↓
  │   静态文件（index.html + JS bundle）
  │       │ 全球 CDN 分发
  │       ↓
  │   用户浏览器（任意城市低延迟）
  │
  └──→ Railway（监听 server/ 目录变化）
          │ docker build
          ↓
      Docker 镜像
          │ 容器启动
          ↓
      Express 服务（常驻进程）
          │ SSE + 文件 I/O
          ↓
      OpenAI 兼容 API

用户请求流程：
用户浏览器
  → 访问 Vercel（获取 HTML/JS）
  → JS 运行，发送 /api/* 请求
  → Vercel rewrites 代理到 Railway
  → Railway Express 处理请求
  → 返回 SSE 流 / JSON 响应
```

## 为什么 Vki 目前是纯本地部署

Vki 有文件系统依赖（data/*.md 文件），上 Railway 需要额外配置：

```
选项 1：Railway 持久卷（Volume）
  → 挂载 /app/data 到持久存储
  → 优点：简单，Railway 一键配置
  → 缺点：卷在区域内，无法全球分布

选项 2：迁移到数据库
  → PostgreSQL（Railway 内置支持）
  → 用 JSON 字段存 frontmatter
  → 优点：真正的多用户、可查询
  → 缺点：需要重写存储层

选项 3：对象存储（S3/R2）
  → 每个 .md 是一个对象
  → 优点：全球分布，无限扩展
  → 缺点：写代码复杂

当前状态：本地开发模式，localhost:3004 + localhost:5179
下一步（Phase 2）：上 Railway + 持久卷
```

## 成本估算（Railway 按量计费）

```
Railway 计费方式：只对运行时计费

实际场景（三个后端项目）：
  - 有请求时：容器运行，按 CPU/内存/带宽计费
  - 无请求时：容器进入空闲（sleep 模式，不计费）
  - 首次请求有冷启动（约 1-2 秒）

预计每月成本（低频使用）：$0 - $5
  - Railway 有 $5/月免费额度
  - 低频使用完全免费
```
