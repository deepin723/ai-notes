## 项目概览

**仓库**：TencentCloud/TencentDB-Agent-Memory  
**今日 Star**：351  
**技术栈**：TypeScript  
**定位**：面向 AI 代理的全本地长期记忆系统，零外部 API 依赖，基于4层渐进式架构

## 基准测试数据

官方报告的性能对比（对比基准：扁平向量存储）：
- **WideSearch 任务**：token 消耗降低 61.38%，任务成功率提升 51.52%（相对值）
- **PersonaMem 任务**：准确率从 48% → 76%（+28 个百分点）

这两个测试都是长期多轮对话场景，正是现有向量存储最容易崩溃的地方。

## 核心架构：两个设计支柱

### 支柱1：分层记忆（按需披露）

**短期记忆**（3层）：
- 底层：工具输出原始引用（完整细节，按需读取）
- 中层：步骤级 JSONL 摘要
- 顶层：轻量 Mermaid 流程图

代理日常只看顶层；出错时按 `node_id` 下钻到对应底层，不把所有原始日志都塞进上下文。

**长期记忆**（4层）：
- L0 对话 → L1 原子事实 → L2 场景块 → L3 用户画像

日常偏好和习惯停在 L3；只有需要时才召回细节。同样逻辑应用于技能生成：执行轨迹 → 通用解决方案模式 → 可复用 Skill/SOP。

### 支柱2：符号记忆（压缩表示）

工具日志通常又长又重复。这个系统不把原始工具输出塞进上下文，而是压缩成紧凑的 Mermaid 图——传达相同的信息但用更少的 token。

存储设计是异构双层：
- 底层（事实、日志、轨迹）：数据库，支持全文检索
- 顶层（画像、场景、流程图）：人类可读的 Markdown

下层保留证据，上层保留结构，完整的无损恢复路径始终存在。

## 为什么扁平向量存储不够

当前大多数 agent 记忆系统的主流方案：嵌入 → 向量数据库 → 相似度检索。

在短对话里工作良好，但在长期多会话场景下有结构性问题：
1. 所有记忆平等对待，没有优先级分层
2. 近期细节和长期偏好混在同一个命名空间
3. 检索要么太宽（噪音太多）要么太窄（漏掉上下文）
4. 原始工具日志不压缩就堆积，token 成本指数级增长

TencentDB-Agent-Memory 本质上是对这一范式的系统性拒绝：**分层符号化而非暴力检索**。

## 我的判断

61% 的 token 减少如果可以复现，这是一个量级上的改进，不是边际优化。

这个架构的设计哲学更接近人类的记忆方式：你不需要回忆上个月每次对话的完整文本，只需要知道"那个用户喜欢简洁的代码，不要多余注释"（L3 画像层）。细节在需要时才被召回，不是一直占用工作记忆。

对独立开发者的实际意义：如果你在用 Claude API 构建多会话代理（比如客服机器人、个人助理、编程代理），现有的"把历史对话全塞进 context"或"向量检索 top-k"两种方案在长期使用后成本会明显攀升。这个4层架构的思路值得在设计阶段就纳入考虑，而不是等 token 账单高到受不了再回来重构。

**实际可用的结论**：先读懂 L0→L1→L2→L3 的分层逻辑（真正适用于你的 agent），再看 Mermaid 压缩的实现细节。即便不直接用这个库，这个架构思路可以移植到任何需要持久化 agent 状态的项目。
