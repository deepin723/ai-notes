## 项目定位

作者换了台新电脑，要重装一堆开发工具（Node/Java/Python/Go/Redis...），嫌麻烦，用了 `mise` 这个**命令行版本管理器**，但觉得 CLI 不够直观，**给 mise 套了一层 Flutter 做的 GUI**。

- 项目名：Mise GUI
- 技术栈：Flutter Desktop（Dart）
- 跨平台：macOS / Windows / Linux
- 仓库：[github.com/likaia/mise_gui](https://github.com/likaia/mise_gui)

核心功能：
- 环境总览（当前装了啥、版本、最近操作）
- 工具版本管理（安装/切换/卸载，带命令预览）
- 项目覆盖（扫描 mise.toml，对比全局差异）
- 配置管理（带 diff 预览编辑）

---

## 先说 mise 是什么（如果你没用过）

`mise` 是 [asdf](https://asdf-vm.com) 的继承者，一个统一的多语言版本管理器：

- 替代 nvm / pyenv / rbenv / gvm / rustup 的版本切换功能
- 支持 Node、Python、Java、Go、Ruby、Deno、Rust 等几十种工具
- 支持项目级 `mise.toml`（像 `.nvmrc` 但支持所有语言）
- 支持任务运行器（像 `make` + `npm scripts`）

一条命令搞定：`mise install node@20` 就完事。

**mise 是过去两年开发者工具链最重要的进化之一**，但知道的人不够多。

---

## 这类"给 CLI 套 GUI"的工具，正在爆发式增长

过去 1-2 年，类似的工具层出不穷：

- **Lazygit** / **Gitui** - git 的 TUI
- **Lazydocker** / **Dockge** - docker 的 TUI/GUI
- **k9s** / **Lens** - kubectl 的 TUI/GUI
- **TablePlus** / **DBeaver** - 数据库 CLI 的 GUI
- **Warp** / **WezTerm** - 终端本身也在加 GUI 化元素
- 现在：**Mise GUI** - mise 的 GUI

---

## 为什么这股风潮起来了

### 1. 开发者工具链变得越来越复杂

10 年前的开发者：一个 Node 版本、一个 MySQL、一个 IDE。

今天的开发者：
- Node（可能同时用 18/20/22）
- Python（可能同时用 3.10/3.12）
- Docker（本地 + 远程多个环境）
- Kubernetes（dev/staging/prod）
- 各种 CLI 工具（gh、vercel、supabase、claude、cursor...）

**心智负担指数级上升**。纯命令行记不过来。

### 2. GUI 降低了"我这个状态到底怎么样"的认知成本

CLI 的问题是：
- 要记命令
- 要看 man page / help
- 要脑内拼接多个命令的输出

GUI 的价值是：
- **全景展示状态**（一眼看清装了啥、哪些项目在用啥）
- **可探索**（不知道能做啥？点点就知道了）
- **带预览/差异**（改之前看清楚后果）

**这在 mise GUI 里体现得很好**：作者特意强调"所有操作都先预览命令"——这是 GUI 真正优于 CLI 的点。**CLI 里你执行了就是执行了**，GUI 里你可以先看后执行。

### 3. Flutter Desktop / Tauri / Electron 让跨平台 GUI 变容易

过去写跨平台桌面 GUI 是**地狱级**难度（Qt、wxWidgets、SWT…）。

现在：
- **Electron** - 用 Web 技术写桌面（VSCode、Discord、Slack）
- **Tauri** - Rust + WebView，轻量
- **Flutter Desktop** - 单代码跨 macOS/Windows/Linux
- **Wails** - Go + Web

**一个会 web 前端的人，周末就能做个桌面 app**。工具门槛降到地板上。

## 作者的选型和几个值得学的工程决策

### 1. 选 Flutter 而不是 Electron

作者的理由：
- 熟悉 Flutter
- UI 写起来直接
- 状态管理（Riverpod）好用
- 打包出来是原生 app，使用门槛低

**Electron 的包大小 ~100MB+，Flutter 桌面 ~20MB**。对"开发者工具"这种要频繁开关的小工具，体积轻很重要。

### 2. 不替代 mise，只做外层壳

作者明说："**这个软件本质上不是替代 mise，而是给 mise 套了一层图形界面**"。

所有操作底层都是 `Process.run("mise ...")`。这有几个好处：
- **mise 原生生态的所有能力都自动继承**
- **mise 更新时 GUI 不需要改**
- **用户切换回 CLI 依然能用**（GUI 和 CLI 完全兼容）

这个设计哲学可以套到很多地方：
- 不要重新发明轮子
- 把 CLI 当黑盒 API 调用
- GUI 层只做"展示 + 交互"

### 3. 处理了一个容易踩的坑：GUI 的 PATH 不等于终端的 PATH

作者发现 Flutter 启动的 GUI 进程**拿不到终端里的 PATH**（因为 shell 启动时加载的 profile 没有被 GUI 继承）。

解法：
```
优先读取常见路径：/opt/homebrew/bin/mise、/usr/local/bin/mise
尝试读取 shell 环境
都找不到 → 引导用户安装
```

**这个坑我自己踩过**，在 Electron 里也有同样问题。是**所有"GUI 调 CLI"工具的共同难点**，值得警惕。

## 我的判断

### ① 开发者工具的 Electron/GUI 层，是个被低估的市场

大家觉得"开发者都用 CLI 才酷"，实际上：
- **中高级开发者**用 CLI，因为他们记得住
- **初级开发者 + 切换项目频繁的人**需要 GUI，因为认知负担
- **老年（35+）开发者**也偏好 GUI——眼睛累

Cursor、Warp 等工具的火爆已经证明：**把开发者体验"可视化 + 智能化"是有巨大市场的**。

### ② "把 CLI 套一层 GUI" 是独立开发者的好切入口

优点：
- **不需要自己做底层逻辑**（CLI 已经做了）
- **产品边界清晰**（围绕一个具体 CLI 工具）
- **用户画像精准**（这个 CLI 的现有用户）
- **技术栈可选**（Flutter/Tauri/Electron 都行）
- **可付费**（Lazygit Pro 模式已经验证可行）

可选方向：
- `kubectl` 的友好 GUI（k9s 之外）
- `docker compose` 的可视化编辑器
- `pnpm` 多 workspace 管理
- `uv` / `poetry` 等 Python 工具的 GUI
- 各家 AI CLI 的统一面板（Cursor、Claude Code、Aider）

### ③ AI 会让这个赛道继续扩张

过去 GUI 是**展示** + **交互**。未来 GUI 是**展示** + **交互** + **智能建议**。

想象一个 "mise GUI + AI"：
- 打开它 → AI 说"你这个项目的 Node 版本比全局老 3 个大版本，有 5 个已知 CVE，建议升级到 20.x"
- 点击"执行升级" → AI 同时检查你的 package.json，告诉你哪些依赖可能不兼容
- 升级完成 → AI 帮你跑一次 `npm install`，并总结变化

**工具链 + AI 助手**是一个巨大的新赛道。

---

## 对我的启示

1. **我自己做工具时，要主动想 GUI 层能不能单独做**。过去我习惯了 CLI，但 GUI 层不等于"降智"，很多场景下它是更好的交互形态。

2. **"不重造轮子，只包一层"**是独立开发者最优策略。自己做轮子慢，包别人的轮子快。护城河在包法不在轮子。

3. **做桌面 GUI 工具我首选 Tauri 或 Flutter**——Electron 太重，包体积大对开发者工具不友好。Tauri 特别合适（Rust + Web UI）。

4. **记下"GUI 的 PATH 问题"这个坑**——未来我做任何 GUI 调 CLI 的工具都会踩。提前规避。

## 延伸：我会想做的那个工具

看完这篇我脑子里冒出来：**AI CLI 统一面板**。

为什么？因为我同时装了：
- `claude`（Claude Code CLI）
- `cursor-agent`（Cursor CLI）
- `gemini`（Gemini CLI）
- `aider`
- 还有各种小的

每个都要单独配 Key、单独查余额、单独管理 session。

一个 GUI 把它们统一起来：
- 一个界面看到所有 AI CLI 的状态、余额、使用量
- 切换工具只要点一下
- 历史 session 集中检索
- 模型对比（同一个任务给不同 CLI 跑，看输出差异）

这个产品大概 **1-2 周能做出 v1**（Tauri + Rust 调 CLI 子进程）。市场大不大不好说，但我自己会用。

**有需求且自己会用 → 值得做**。这是所有好独立项目的共同点。
