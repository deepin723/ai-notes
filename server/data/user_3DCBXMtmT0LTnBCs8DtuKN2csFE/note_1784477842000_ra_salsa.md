> 这篇讲 rust-analyzer 能"每次按键都秒回"的核心机制——Salsa。属于 [[note_1784477841000_ra_overview]] 里"Analysis 层"的底座。

## 一、问题：为什么不能每次都全量算

IDE 的典型场景：用户每敲一个字符就要重新分析。一个稍大的 crate 有几千个文件、几万个定义，如果每次按键都从头 parse + 类型推断一遍，单次可能要好几秒——完全没法用。

朴素优化是"只重算改动的那个文件"，但远远不够：你在 `lib.rs` 里改了一个 `pub struct` 的字段，所有引用它的文件都得跟着重算。"哪些东西受影响"这件事本身就需要追踪。

**Salsa 就是来干这个的**：把所有计算拆成一个个小函数（叫 **query**），自动追踪 query 之间的依赖，输入变了只重算"真正受影响"的那部分。

## 二、Salsa 的心智模型

把整个分析看成一张**查询依赖图**：

```
   input: 文件内容           input: Cargo.toml
        │                          │
        ▼                          ▼
   parse(file) ──→ ast       crate_graph
        │                          │
        └──────────┬───────────────┘
                   ▼
            name_resolution(crate)
                   │
        ┌──────────┼──────────┐
        ▼          ▼          ▼
    infer(fn_a) infer(fn_b) infer(fn_c)
                   │
                   ▼
            diagnostics
```

每个方框是一个 query。query 的特点：

1. **纯函数**：同样的输入一定给同样的输出（除了读"数据库"里的其它 query）。
2. **可记忆（memoize）**：算过的结果缓存起来。
3. **依赖可追踪**：query A 在算的时候调用了 query B，Salsa 就记下"A 依赖 B"。

## 三、red-green：变了什么就只重算什么

Salsa 借鉴了 Roslyn 的 **red-green** 思路（rowan 的语法树也用了类似概念，见 [[note_1784477843000_ra_syntax_tree]]）：

- **green（绿）= 没变**：这个 query 的所有输入都没动，缓存直接复用，零成本。
- **red（红）= 需要重算**：上游某个依赖被标红了，这个 query 可能受影响，要重算。

传播规则：一个 query 变红，**只**把"调用了它的"那些 query 标红，其余不动。因为 Salsa 记了依赖图，它能精准地只染红一条链。

举个具体例子：

```
1. 初始状态：所有 query 都是 green，结果都缓存着
2. 用户改了 main.rs（只改了一个函数体）
   → parse(main.rs) 变 red
   → 但 parse(lib.rs) 仍 green（没动）
3. 重算 parse(main.rs) → 新 AST
4. name_resolution 依赖 parse → 可能变 red → 重算
   但如果 name_resolution 发现"导出的符号没变"，它可以判定自己仍 green
   → 这一步叫 "verified green"，关键优化
5. infer(别的没碰的函数) 全程 green，直接复用缓存
```

第 4 步是精华：**"我的输入 query 重算了，但它的结果没变，所以我也不用重算"**。这让"改一个函数体不影响别人"的场景几乎零成本。

## 四、代码长什么样（概念）

Salsa 现在大量用宏/属性来声明 query，大致是：

```rust
#[salsa::input]
struct FileText {
    #[return_ref]
    text: String,
}

#[salsa::tracked]
fn parse(db: &dyn Db, file: FileText) -> SyntaxNode {
    // 纯函数：从 file 的文本 parse 出语法树
    // 调用了 file.text(db) → Salsa 自动记下依赖
    let src = file.text(db);
    rowan::parse(src)
}

#[salsa::tracked]
fn type_of(db: &dyn Db, file: FileText, expr_id: ExprId) -> Type {
    let ast = parse(db, file);       // 依赖 parse
    infer(db, file)                  // 依赖 infer
        .type_of(expr_id)
}
```

- `#[salsa::input]`：标记一个**输入**——这是依赖图的根，外部世界喂进来的数据（文件内容、配置）。
- `#[salsa::tracked]`：标记一个**派生 query**——它的输入全是其它 query，结果会被缓存。
- `db`（database）：所有 query 的入口，你调 `type_of(db, ...)`，Salsa 负责查缓存/算/记依赖。

第一次调 `type_of` 会层层往下算，建好依赖图和缓存。第二次调（什么都没改）直接命中缓存。改了文件后只重算染红的那条链。

## 五、为什么这对 IDE 是绝配

| IDE 行为 | Salsa 怎么帮 |
|----------|-------------|
| 每次按键 | 只染红改动文件相关的 query，毫秒级 |
| 在不完整代码上工作 | query 容错返回部分结果，下游照样能算 |
| 跨文件跳转 | name res 结果缓存，跳转查的是缓存不是重算 |
| hover 看类型 | type_of 命中缓存，几乎瞬时 |

如果没有 Salsa 这套机制，r-a 根本不可能在百万行项目上做到实时响应。

## 六、一个类比

如果你写过前端，Salsa ≈ **Redux 的 selector + reselect 的 memoize**，但更强：reselect 只 memoize 单个 selector 的最后输入；Salsa 记的是**整张依赖图**，能在任意输入变化时算出最小重算集。

如果你熟悉数据库：Salsa ≈ **物化视图的增量维护**——view 依赖 base table，base 变了只刷新受影响的 view，而不是全表重算。

## 七、对学 Rust 的启示

Salsa 是"用 Rust 写领域特定框架"的范本：

- 用 trait（`&dyn Db`）定义 query 接口，用宏生成实现——Rust 的元编程能力展示。
- 不可变数据 + `Arc` 共享是 Salsa 能追踪依赖的前提（可变状态没法做依赖图）。
- 它把"性能关键路径"做成了纯函数，副作用隔离在 input 层——Rust 风格的架构。

> 入门不用学 Salsa 怎么实现，先记住这个模型：**把计算拆成纯函数，记依赖图，输入变了只重算受影响的部分**。写自己的 Rust 项目时遇到"需要反复重算一大坨"的场景，可以想想能不能套这个结构（哪怕手写 memoize）。

## 八、一句话总结

Salsa 让 r-a 做到"按键即响应"：把分析拆成一堆纯函数 query，记下它们之间的依赖，输入变化时用 red-green 机制只染红、只重算受影响的那条链，没碰的全部复用缓存。
