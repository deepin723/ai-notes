## 项目是什么

FastMCP 是 Prefect 维护的 Python MCP 框架，Trending 当天新增 96 个 star。它的使用方式很像现代 Web 框架：把一个 Python 函数标成 `@mcp.tool`，框架负责生成 schema、校验和协议层连接；同时提供 server、client 和在会话内渲染交互 UI 的 Apps 三个面向。

README 的主张很清楚：开发者应该专注工具的业务逻辑，而不必重复处理 transport 协商、认证和协议生命周期。它还声称 FastMCP 1.0 的部分能力已被并入官方 MCP Python SDK，说明这个项目对协议生态有历史影响。

## 为什么重要

MCP 看似只是“暴露几个函数给模型”，但一旦进入生产，问题会迅速变成：输入 schema 是否稳定、连接如何恢复、鉴权怎么做、远端 server 怎样发现、工具怎样被治理。把这些横切复杂度封装在框架中，能降低每个团队各自实现一套半成品协议适配器的风险。

项目同时强调客户端能力很关键。只会写 server 的团队往往会把调用侧留给 agent 框架“自行处理”；但真实系统需要统一处理远程连接、传输方式、认证与错误。FastMCP 把 client 当一等公民，正好补上这个缺口。

## 我的判断

框架能减少协议摩擦，但不能替团队定义工具边界。对模型暴露的函数仍应遵循最小权限、明确副作用、可审计输入输出，并为危险操作加确认与幂等设计。否则“写一个 decorator 就能上线”的体验，会让 MCP 服务器变成新的内部攻击面。

选择 FastMCP 时，先用一个无副作用的读工具验证 schema、日志、认证和 deployment，再逐步加入写操作；不要把已有的 REST API 全量机械映射为 tools。

## 实际可用结论

- MCP 框架应替代样板协议代码，不替代权限设计与产品边界。
- 工具函数优先小而明确；写操作要有审计、确认和失败恢复策略。
