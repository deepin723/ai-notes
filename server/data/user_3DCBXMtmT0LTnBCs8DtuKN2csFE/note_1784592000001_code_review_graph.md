## 项目是什么

`code-review-graph` 是一个面向 AI 代码评审的本地优先工具。它用 Tree-sitter 把函数、类、导入、调用关系和测试关系解析成图，再通过 MCP 把“这次改动真正会波及什么”交给 AI。核心目标不是让模型读得更快，而是让模型少读不相关的文件。

GitHub Trending 当天显示它获得 1,833 个新增 star。README 给出的使用路径很直接：安装、`build` 解析代码库，再把图作为 MCP 上下文供 Codex、Claude Code、Cursor 等工具调用。它还主张在保存或提交时增量更新图，而不是全量重建。

## 为什么值得关注

AI 编程工具在大型仓库里最昂贵的动作，常常不是生成代码，而是为了“保险”而反复读取大量上下文。传统 RAG 按文本相似度找文件，容易遗漏调用链；而依赖图把问题改写为：变更的函数有哪些调用者、下游依赖和缺失测试？这正是评审场景更接近的检索单位。

项目的价值因此不只在 token 节省。若爆炸半径能被结构化表示，评审输出就可以更具体：某个改动影响哪些执行流、哪些测试尚未覆盖、风险来自接口变化还是数据流变化。README 还强调本地构图，源代码不必离开开发机，这对企业评审也更容易接受。

## 我的判断

这类产品真正的门槛不在“能否建图”，而在图是否足够可信。动态语言、反射、代码生成、跨服务调用和框架约定都会让静态关系不完整；若它把不确定性说成确定结论，反而会造成漏检。因此最合理的定位是“帮助 AI 缩小阅读范围的证据层”，不是替代测试或人工判断的裁决器。

对日常工程而言，先在 PR 评审或重构前使用，收益最容易验证：比较启用前后的实际读取文件数、遗漏缺陷和测试建议质量。如果这些指标稳定，再把它接入 commit hook 或 CI。

## 实际可用结论

- 大仓库的 AI 评审应优先拿到依赖关系，而不是把上下文窗口继续加大。
- 落地时把图结果当“优先级提示”，仍要让测试、运行时日志和人工审查共同兜底。
