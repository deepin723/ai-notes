## 项目概览

**仓库**：Leonxlnx/taste-skill  
**今日 Star**：1,453（GitHub Trending 日榜 #5）  
**定位**：给 AI coding agent 提供"好品味"，阻止它生成千篇一律的平庸输出

## 核心问题

当前 AI coding agent（Claude Code、Codex、Cursor 等）存在一个共性问题：代码能跑，但是**平庸**。

具体表现：
- 命名总是 `data`、`result`、`temp`、`handler`，毫无表达力
- 函数签名总是选最保守的写法，没有对问题本质的理解
- 错误处理总是 try-catch 包全部，没有层次
- 注释总是解释"做了什么"，从不解释"为什么这样做"
- 抽象层次总是停在表面，不往下挖一层

这些问题让 AI 生成的代码"能 merge 但不值得学习"，也让 code review 成了纠正鸡毛蒜皮的过程而非技术讨论。

## Taste-Skill 的方式

该项目通过向 AI agent 注入一套"taste"规则集（类似 Claude Code 的 CLAUDE.md 或系统级 skill）来干预代码生成质量，强制 agent 在生成代码时遵循审美约束。

规则涵盖：
- 命名哲学：名字要揭示意图，不要揭示实现
- 抽象选择：选择最能表达领域概念的那层，不要过高也不要过低
- 函数设计：一个函数只做一件有意义的事，不是一件机械的事
- 错误处理：按照错误的重要性分层，不要平铺直叙
- 代码节奏：短函数之间的间距、长函数的拆分时机

本质上这是一套**可检查的工程美学规则**，从"这段代码能不能跑"上升到"这段代码值不值得读"。

## 为什么今天大量关注

这个方向切中了一个越来越多人意识到的痛点：**AI 把写代码的速度问题解决了，但把代码质量的天花板拉低了**。

类似的工具和讨论正在涌现：
- GitHub Trending 同期还有 `addyosmani/agent-skills`（生产级 AI agent 工程 skills）
- 大量 CLAUDE.md 模板开始强调"代码风格要求"而不只是"功能需求"
- "vibe coding"这个词开始带有贬义色彩，对应的是没有品味约束的快速生成

## 我的判断

这个工具击中了一个真实需求，但它的方式值得审视。

**有效的部分**：把隐性的"好代码"直觉转化为可描述、可传达给 AI 的规则，这是有价值的工程化工作。就像 linting rules 把代码规范固化一样，taste rules 尝试固化设计哲学。

**局限的部分**：代码的"好品味"很难脱离领域上下文——一段好的金融计算代码和一段好的 UI 组件代码遵循不同的审美准则。通用规则很容易变成另一种形式的"模板化"。

**真正的核心问题**：AI agent 生成平庸代码，根本原因是它在优化"通过测试"而不是"有表达力"。这需要更深层的 RLHF 或训练数据上的改变，而不只是 prompt 层面的过滤。

**实际可用的结论**：在等待模型本身改进之前，把 taste-skill 的规则纳入自己项目的 CLAUDE.md 是合理的短期方案。但要保持警惕：规则一多，agent 会开始机械地满足规则检查，这又是另一种形式的平庸。
