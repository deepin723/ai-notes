## 一、整体架构图

```
用户浏览器
   │
   ├─ 前端 (Vercel)  ←── @clerk/vue  ─┐
   │   Vue 3 App                      │  Clerk SDK（前端）
   │   - 渲染登录界面                  │  - 管理 Session Token
   │   - 携带 JWT 调用 API             │  - 提供 useAuth / useUser
   │                                  ┘
   │  HTTP + Authorization: Bearer <token>
   │
   └─ 后端 (Railway) ←── @clerk/express ─┐
       Express Server                     │  Clerk SDK（后端）
       - 验证 JWT                          │  - clerkMiddleware()
       - 取出 userId                       │  - getAuth(req)
       - 读写 data/{userId}/*.md           └─ 请求 Clerk JWKS 公钥
```

核心关系：**Clerk 负责身份认证，Railway 负责承载后端服务和保存密钥，两者通过 JWT 串联。**

---

## 二、Clerk 是什么

Clerk 是一个"Auth-as-a-Service"平台，可以理解为把整套用户系统（注册/登录/OAuth/MFA/用户管理后台）全部外包出去，项目只需集成它的 SDK。

**Clerk 提供的核心能力：**

| 能力 | 说明 |
|------|------|
| 托管登录 UI | `<SignIn />` 组件，开箱即用 |
| Session 管理 | 自动处理 Cookie / Token 的刷新 |
| JWT 签发 | 每次调用 `getToken()` 返回有时效的 JWT |
| 后端 SDK | 验证 JWT、解析 userId |
| 用户管理后台 | clerk.com Dashboard，查看所有用户 |

## 三、前端侧：@clerk/vue 做了什么

### 3.1 ClerkProvider 初始化

在 `main.ts` 中挂载：

```ts
import { clerkPlugin } from '@clerk/vue'

app.use(clerkPlugin, {
  publishableKey: import.meta.env.VITE_CLERK_PUBLISHABLE_KEY,
})
```

`publishableKey`（`pk_test_...`）是公开的，可以写进前端代码或 `.env`。它的作用是告诉 Clerk SDK 这个应用是谁，从而知道去哪个 Clerk 实例获取配置。

### 3.2 未登录时展示 `<SignIn />`

```vue
<!-- App.vue -->
<div v-if="!isSignedIn" class="auth-wall">
  <SignIn />
</div>
```

`isSignedIn` 来自 `useAuth()`，它是一个响应式 `Ref<boolean>`。Clerk 在初始化时会检查本地 Cookie / localStorage 里有没有有效 Session，如果有就自动恢复登录状态，页面刷新不会掉线。

`<SignIn />` 组件完全由 Clerk 托管渲染，包括表单验证、OAuth 跳转（Google / GitHub 等）、邮件验证码等流程，开发者零代码实现。

### 3.3 获取用户信息：useUser()

```ts
import { useUser } from '@clerk/vue'

const { user } = useUser()

// user.value.fullName          → "铁头娃"
// user.value.imageUrl          → 头像 URL
// user.value.primaryEmailAddress?.emailAddress → "xxx@gmail.com"
// user.value.id                → "user_3DCBXMtmT0LTnBCs8DtuKN2csFE"
```

`user` 是一个 `Ref`，在组件中可以直接用于模板绑定，完全响应式。这些数据来自 Clerk 的服务器，SDK 初始化时会自动拉取并缓存。

### 3.4 获取 JWT Token：getToken()

```ts
import { useAuth } from '@clerk/vue'

const { getToken } = useAuth()

// 每次调用都会返回一个新鲜的 JWT（自动刷新）
const token = await getToken()
// → "eyJhbGciOiJSUzI1NiIsI..."（RS256 签名的 JWT）
```

这个 JWT 的有效期通常是 **60 秒**，每次调用 `getToken()` 会自动判断是否过期并刷新，开发者不需要手动管理 token 刷新逻辑。

### 3.5 携带 Token 调用后端

```ts
// NoteApp.vue 中的 authFetch 封装
const authFetch = async (url: string, options: RequestInit = {}) => {
  const token = await props.getToken()   // ← 拿到新鲜 JWT
  return fetch(url, {
    ...options,
    headers: {
      ...(options.headers as Record<string, string> || {}),
      ...(token ? { Authorization: `Bearer ${token}` } : {}),  // ← 塞进 Header
    },
  })
}
```

所有 API 请求都通过这个 `authFetch` 发出，后端拿到的 `Authorization: Bearer xxx` 就是 Clerk 签发的 JWT。

### 3.6 退出登录：useClerk()

```ts
import { useClerk } from '@clerk/vue'

const { signOut } = useClerk()

// 点击退出按钮
<button @click="signOut()">退出</button>
```

`signOut()` 会清除本地 Session 和 Cookie，同时通知 Clerk 服务端使 Session 失效，之后 `isSignedIn` 自动变为 `false`，页面回到登录界面。

## 四、后端侧：@clerk/express 做了什么

### 4.1 clerkMiddleware() 全局挂载

```js
import { clerkMiddleware, getAuth } from '@clerk/express'

app.use(clerkMiddleware())
```

这一行让所有请求都经过 Clerk 中间件。中间件会：
1. 从请求 Header 中提取 `Authorization: Bearer <token>`
2. 向 Clerk 服务器拉取 **JWKS 公钥**（缓存复用）
3. 用公钥验证 JWT 的 RS256 签名
4. 验证通过后把解析结果（包含 `userId`）挂在 `req.auth` 上

`clerkMiddleware()` 本身**不拒绝**未登录请求，它只是「处理」。真正的鉴权拒绝在自定义中间件 `requireUser` 里做。

### 4.2 requireUser 中间件：提取 userId

```js
const requireUser = (req, res, next) => {
  const { userId } = getAuth(req)       // ← 从 req.auth 取出 userId
  if (!userId) return res.status(401).json({ error: '未登录' })
  req.userId = userId                   // ← 挂到 req 上，后续 handler 使用
  next()
}
```

`getAuth(req)` 是 Clerk 提供的工具函数，从已经处理过的请求中安全地取出认证信息。`userId` 就是 Clerk 用户的唯一 ID，格式固定：`user_xxxx`。

### 4.3 基于 userId 的数据隔离

```js
// 每个用户有独立目录
const userDir = (userId) => {
  const dir = path.join(BASE_DATA_DIR, userId)
  // → server/data/user_3DCBXMtmT0LTnBCs8DtuKN2csFE/
  if (!fs.existsSync(dir)) fs.mkdirSync(dir, { recursive: true })
  return dir
}

// 所有读写操作都带 userId
app.get('/api/notes', requireUser, (req, res) => {
  res.json(listNotes(req.userId))   // ← 只读当前用户的笔记
})
```

这样天然实现了多用户数据隔离：A 用户永远只能看到和修改自己目录下的笔记，不会互相串数据。

## 五、JWT 完整流转过程

```
1. 用户打开页面
   └─ Clerk SDK 检查 Cookie → 有效 Session → isSignedIn = true

2. 前端发起 API 请求
   └─ authFetch() 调用 getToken()
      └─ Clerk SDK 检查 token 是否过期
         ├─ 未过期 → 直接返回缓存 token
         └─ 过期   → 用 refresh_token 向 Clerk 换新 token

3. 请求到达后端
   └─ clerkMiddleware() 处理
      └─ 提取 Bearer token
         └─ 用 Clerk JWKS 公钥验证 JWT 签名
            ├─ 验证失败 → req.auth.userId = null
            └─ 验证成功 → req.auth.userId = "user_3DCBXMtmT0LTnBCs8DtuKN2csFE"

4. requireUser 中间件
   └─ userId 存在 → next()，进入业务 handler
   └─ userId 不存在 → 401 返回

5. 业务 handler
   └─ req.userId 指向当前用户
      └─ 读/写 server/data/{userId}/*.md
```

## 六、Railway 承担了什么角色

Railway 是这套架构的**后端运行环境**，它做了三件事：

### 6.1 托管 Express 服务

```
GitHub main 分支 → Railway 自动检测 Dockerfile → 构建 → 部署
```

每次 `git push main`，Railway 检测到变化，重新 build Docker 镜像，零停机切换到新版本。后端代码运行在 Railway 的容器里，对外暴露一个 HTTPS URL，Vercel 上的前端通过这个 URL 调用 API。

### 6.2 安全存储环境变量

后端需要两个 Clerk 密钥，它们不能写进代码或 git：

| 变量名 | 作用 | 可见性 |
|--------|------|--------|
| `CLERK_SECRET_KEY` | 后端 SDK 向 Clerk 验证请求身份 | 只在 Railway 容器内可见 |
| `CLERK_PUBLISHABLE_KEY` | `clerkMiddleware()` 初始化时需要 | 只在 Railway 容器内可见 |

```js
// Clerk SDK 自动读取这两个环境变量，不需要手动传入
app.use(clerkMiddleware())
// 等价于：clerkMiddleware({ secretKey: process.env.CLERK_SECRET_KEY, ... })
```

`CLERK_SECRET_KEY`（`sk_test_...`）是真正的机密，如果泄露，攻击者可以冒充后端向 Clerk 发请求。Railway 的环境变量面板加密存储，不会出现在构建日志或容器文件系统里。

### 6.3 持久化笔记文件

```
Railway 容器文件系统
└── server/
    ├── data/
    │   └── user_3DCBXMtmT0LTnBCs8DtuKN2csFE/
    │       ├── note_xxx.md
    │       └── note_yyy.md
    └── index.js
```

笔记以 `.md` 文件形式存在容器的本地文件系统中。由于 git 中也跟踪了这些文件（`.gitignore` 未忽略 `server/data/`），每次部署时这些文件会随代码一起被打包进镜像，相当于"代码即数据"的简单方案。

> ⚠️ **注意**：Railway 默认的文件系统是**非持久化**的，容器重启数据会丢失。这个项目能持久化是因为笔记文件在 git 里跟踪，每次 build 都带进镜像。如果未来改成"运行时写入不提交 git"，就需要挂载 Railway 的 Volume。

## 七、前后端密钥分工

| 密钥 | 存放位置 | 用途 |
|------|----------|------|
| `VITE_CLERK_PUBLISHABLE_KEY` | Vercel 环境变量 / `.env` | 前端 SDK 初始化，识别 Clerk 应用 |
| `CLERK_SECRET_KEY` | Railway 环境变量 | 后端 SDK 验证 JWT，调用 Clerk 管理 API |
| `CLERK_PUBLISHABLE_KEY` | Railway 环境变量 | `clerkMiddleware()` 初始化需要 |

前端的 publishableKey 本质上是公开的（会出现在打包后的 JS 里），不是机密。后端的 secretKey 绝对不能暴露到前端，所以只存在 Railway 服务端环境变量中。

---

## 八、一句话总结

**Clerk** 是身份证系统（颁发 JWT、管理用户），**前端 SDK** 负责登录 UI 和 token 携带，**后端 SDK** 负责验证 token 并取出 userId，**Railway** 是安全运行后端的容器平台（托管服务 + 保管密钥 + 存储数据）。
