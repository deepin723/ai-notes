## 项目是什么

jcode 把自己定位为下一代 coding agent harness，Trending 当天新增 568 个 star。它主打多会话工作流、深度可定制和资源效率，采用 Rust 实现，并将本地 embedding、语义记忆、会话检索、侧边栏和多 agent 协作做进同一套终端体验。

README 给出一组内存与启动时间对比，意在说明 agent 工具在单会话和多会话并存时的运行成本。项目还提供 swarm：多个 agent 在同一仓库里协作时，若某个 agent 修改了另一个已读文件，系统会通知相关 agent 重新检查差异。

## 为什么有意思

当前 coding agent 的真实瓶颈不止模型能力，还包括长时间运行后的上下文管理、多个任务并行的冲突、以及本地资源消耗。jcode 把“记忆”和“协作一致性”前置到 harness 层，说明它想解决的是连续开发过程，而不是单次问答。

它的记忆方案包含自动提取、语义召回、定期整合和显式读写工具。它的协作方案则把文件变更当成需要传播的事件。两者共同指向一个结论：agent 系统开始需要像操作系统一样管理状态与资源。

## 我的判断

README 中的性能对比值得关注，但应看作特定机器、版本与配置下的测量，而不是普适排名。对实际用户，更重要的是它在长任务下会不会误召回旧记忆、多个 agent 是否真的减少冲突、以及是否能在出现异常时让人理解系统状态。

我尤其认同“变更通知”方向：并行 agent 最大风险不是速度，而是彼此依据过期代码继续工作。若 harness 能把冲突显式化，再配合清晰的任务边界，才可能把并发变成净收益。

## 实际可用结论

- 评估 agent harness 时，把多会话稳定性、可观测性和冲突处理与模型质量一起看。
- 性能测试应在自己的 repo、模型和并发数下复现，避免只看宣传 benchmark。
