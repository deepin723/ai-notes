## 项目定位

OpenWork 是一个跨 macOS、Windows、Linux 的开源桌面应用，目标是让 AI 工作流可以被分享和重复使用。它把自己定位为 Claude Cowork 与 Codex 的开源替代，但更准确地说，它想做的是 Agent 能力的“分发层”。

用户可以把同一个 OpenWork MCP 接到 Codex、Claude Code、Cursor 或其他兼容客户端，然后复用同一组技能、MCP 连接和第三方服务。客户端只看到两个抽象工具：`search_capabilities` 用于发现能力，`execute_capability` 用于执行能力。具体能力从哪里来、谁有权使用，由 OpenWork 统一处理。

## 团队场景为何重要

个人使用 Agent 时，配置散落在不同工具里只是麻烦；到了团队里，它会变成治理问题：同一个连接要重复配置，权限无法统一撤回，技能版本各自漂移，也很难知道谁调用了什么。

OpenWork Den 提供组织控制面，可分配模型供应商、邀请成员、建立团队、限制本地模型、控制桌面版本，并通过 marketplace 发布技能与插件。它还尝试兼容 Anthropic 风格插件，让已有生态不必全部重写。

## 工程上的细节

项目为多 worktree 开发提供独立 profile、自动选择 Electron CDP 端口和 Vite 端口，并处理 macOS keychain 弹窗导致主循环阻塞的问题。这个看似细碎的设计反映出项目确实在面对多实例、多人协作和真实开发环境，而不是只做一层 UI 包装。

## 我的判断

OpenWork 押注的是一个很可能成立的趋势：未来用户不会只使用一个 Agent，但希望能力、授权与组织规则只配置一次。它的机会类似身份系统或 API 网关——价值来自成为统一入口，而不是自己拥有最强模型。

风险也同样明显：一旦成为能力中枢，它就会接触大量高权限连接。安全隔离、审计日志、最小权限和供应链验证必须比“安装更方便”更优先，否则统一入口也会成为统一攻击面。

## 对我的启示

评估这类平台不能只看支持多少 MCP，而应检查授权范围能否逐项查看、是否支持撤销、执行前是否显示影响对象、以及团队管理员能否追溯每次调用。
